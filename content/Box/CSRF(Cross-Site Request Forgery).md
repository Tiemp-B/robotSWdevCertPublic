# Summary

CSRF(Cross-Site Request Forgery)는 로그인된 사용자가 **자신도 모르게 공격자가 의도한 요청을 정상 서버로 보내게** 만드는 공격으로, 서버가 요청의 진짜 출처를 검증하지 않을 때 성립한다.

# Notes

<aside>CSRF의 동작 방식</aside>

1. 사용자가 정상 사이트(예: 은행, 관제 시스템)에 로그인해 인증 쿠키를 발급받은 상태를 유지
2. 이 상태로 공격자가 만든 악성 페이지를 열람(피싱 메일 링크, 악성 사이트 방문 등)
3. 그 페이지에 숨겨진 요청(자동 제출되는 `<form>`, 이미지 태그의 `src`에 위장된 요청 URL 등)이 사용자 모르게 브라우저를 통해 **정상 사이트로 전송**됨
4. 브라우저는 요청을 보낼 때 해당 도메인의 인증 쿠키를 관례대로 자동 첨부하므로, 서버는 이를 사용자 본인이 직접 보낸 정상 요청으로 착각하고 처리함

<aside>공격이 성립하는 조건</aside>

- 서버가 **요청의 출처(Origin/Referer)를 검증하지 않음**
- 상태를 변경하는 요청(비밀번호 변경, 송금, 로봇 명령 전송 등)이 **예측 가능한 파라미터만으로 구성**되어 있어 공격자가 미리 요청 형태를 만들어둘 수 있음
- 인증 방식이 **쿠키 기반**이라 브라우저가 요청 시 자동으로 인증 정보를 첨부함(반면 매 요청마다 별도 토큰을 헤더에 직접 실어야 하는 인증 방식은 CSRF에 상대적으로 덜 취약함)

<aside>로봇 시스템에서의 위험</aside>

**예시**: 로봇 관제 대시보드가 CSRF에 취약하면, 관리자가 로그인된 상태에서 악성 페이지를 열람하는 것만으로 "긴급 정지 해제", "로봇 이동 명령" 같은 요청이 관리자 모르게 전송되어 실행될 수 있다.

<aside>방지</aside>

- **CSRF 토큰**: 서버가 폼·요청마다 예측 불가능한 토큰을 발급하고, 요청에 그 토큰이 정확히 포함되어야만 처리 — 공격자는 사용자의 브라우저에 있는 이 토큰 값을 알 수 없어 위조가 불가능해짐
- **SameSite 쿠키 속성**: 쿠키에 `SameSite=Strict` 또는 `Lax`를 설정하면, 다른 사이트에서 발생한 요청에는 브라우저가 쿠키를 자동으로 첨부하지 않아 공격이 원천 차단됨
- **커스텀 헤더 검증**: AJAX 요청에만 존재하는 커스텀 헤더(예: `X-Requested-With`)를 서버가 확인 — 단순 HTML 폼 제출로는 이 헤더를 위조하기 어려움

---

<aside>핵심 정리</aside>

- CSRF는 서버가 요청 출처를 검증하지 않을 때, 인증된 사용자의 권한으로 위조된 요청이 처리되는 공격이다
- 브라우저가 쿠키를 자동 첨부하는 특성이 공격의 성립 조건이 된다
- CSRF 토큰, SameSite 쿠키, 커스텀 헤더 검증이 기본 방어책이다
