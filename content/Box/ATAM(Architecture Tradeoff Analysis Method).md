# Summary

ATAM은 소프트웨어 아키텍처가 **여러 품질 속성(성능·보안·수정용이성 등) 요구사항을 얼마나 만족하는지, 그리고 그 속성들이 서로 어떤 트레이드오프 관계에 있는지**를 이해관계자 참여 워크숍을 통해 분석하는 아키텍처 평가 기법이다.

# Notes

<aside>ATAM이 찾으려는 것</aside>

| 개념 | 의미 |
|---|---|
| 민감점(Sensitivity Point) | 아키텍처 결정 하나를 바꿨을 때 특정 품질 속성이 크게 좌우되는 지점 |
| 트레이드오프 지점(Tradeoff Point) | 한 품질 속성을 개선하면 다른 품질 속성이 나빠지는 지점(예: 보안 강화 시 성능 저하) |
| 리스크(Risk) | 향후 문제가 될 수 있는 아키텍처 결정 |
| 무리스크(Non-risk) | 검토했지만 문제없다고 확인된 결정 |

"ATAM의 목적은 아키텍처의 코드 결함을 정적 분석 도구로 찾아내는 것이다"라는 서술은 오답이다 — ATAM은 코드 레벨 결함 탐지 도구가 아니라, **품질 속성 간 트레이드오프를 이해관계자와 함께 분석하는 평가 방법론**이다.

<aside>유틸리티 트리(Utility Tree)</aside>

ATAM은 시나리오를 **3단계 계층 구조**로 정리한다 — 최상위는 품질 속성(성능·보안 등), 중간은 그 속성의 세분화(예: 성능→지연시간), 최하위는 자극-반응-측정으로 기술되는 구체적 시나리오다. 이 유틸리티 트리를 통해 이해관계자들이 어떤 시나리오가 가장 중요한지 우선순위를 매길 수 있다.

<aside>결합도 메트릭과의 관계</aside>

ATAM이 다루는 "수정 용이성" 같은 품질 속성은 [[결합도(Coupling)]]·[[응집도(Cohesion)]] 같은 정량적 메트릭으로 뒷받침되는 경우가 많다 — ATAM 워크숍에서 "이 모듈은 결합도가 높아 유지보수성이 낮다"는 식으로 메트릭을 근거로 활용한다.

---

<aside>핵심 정리</aside>

- ATAM은 아키텍처가 여러 품질 속성을 얼마나 만족하는지와 그 속성 간 트레이드오프를 분석하는 평가 기법이다
- 민감점·트레이드오프 지점·리스크·무리스크를 식별하는 워크숍 방식이며, 코드 결함 탐지 도구가 아니다
