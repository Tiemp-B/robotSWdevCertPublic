# Summary

로봇 원격제어기 인터페이스는 운영자가 로봇과 물리적으로 떨어진 곳에서 명령을 내리고 상태를 확인할 수 있게 하는 인터페이스로, **클라이언트(조작 화면) — 통신 채널 — 로봇 측 제어기**라는 세 요소로 구성된다. 로컬 제어와 달리 네트워크를 반드시 거치므로 통신 프로토콜 선택, 명령이 오가는 통신 패턴, 안전한 조작 화면(HMI) 설계, 지연시간 관리라는 네 가지 문제를 함께 다뤄야 하며, 이 원격제어기의 대표적 실물이 **[[6. 로봇 교시 프로그래밍과 오프라인 프로그래밍|티치 펜던트]]**다.

# Notes

<aside>원격제어와 로컬제어의 차이</aside>

로컬 제어는 로봇에 직접 부착된 조작기·배선으로 명령을 전달해 지연이 거의 없고 신뢰성이 높다. 원격 제어는 네트워크를 거쳐야 하므로 **지연시간, 패킷 유실, 보안 위협**이라는 로컬 제어에는 없던 문제가 새로 생긴다. 원격제어기 인터페이스의 설계 고려사항 대부분은 결국 이 "네트워크를 거친다"는 제약에서 비롯된다.

<aside>원격제어기 인터페이스의 구성 요소</aside>

| 구성 요소 | 역할 |
|---|---|
| 클라이언트(조작 UI/HMI) | 운영자가 명령을 입력하고 로봇 상태를 확인 |
| 통신 채널(프로토콜) | 명령과 상태 데이터를 네트워크로 전달 |
| 로봇 측 수신부(제어기) | 수신한 명령을 실제 동작으로 변환하고, 상태를 다시 보고 |

<aside>이 세세항목의 구성</aside>

이후 페이지는 이 구성 요소를 각각 다룬다: [[2. 원격제어 통신 프로토콜 개요|통신 프로토콜]](통신 채널이 어떤 성능 지표로 선택되는가), [[3. 통신 모델(발행-구독·요청-응답·액션)|통신 모델]](명령·상태가 오가는 패턴), [[4. HMI 설계 원칙|HMI 설계]](클라이언트 조작 화면의 안전성), [[5. 네트워크 지연과 QoS|네트워크 지연과 QoS]](통신 채널의 실시간성 확보), [[6. 로봇 교시 프로그래밍과 오프라인 프로그래밍|로봇 교시·오프라인 프로그래밍]](원격제어기의 대표적 실물인 티치 펜던트로 로봇에게 동작을 가르치는 방법).

<aside>예시 — 로봇 원격제어 시스템 전체 흐름</aside>

**예시**: 운영자가 웹 대시보드(클라이언트)에서 정지 버튼을 클릭하면, 명령이 통신 채널을 통해 전송되고, 로봇 제어기가 이 명령을 수신해 실제 정지 동작을 수행한 뒤 그 결과 상태가 다시 클라이언트에 반영된다. 이 "클릭→정지→화면 갱신" 한 번의 흐름 안에 이 세세항목의 다섯 페이지가 다루는 요소가 모두 관여한다.

<aside>핵심 정리</aside>

- 원격제어기 인터페이스는 **클라이언트(HMI) — 통신 채널(프로토콜) — 로봇 측 제어기** 세 구성 요소로 이뤄진다
- 원격 제어는 로컬 제어와 달리 네트워크를 거치므로 지연·유실·보안이라는 새로운 문제를 안게 된다
- 나머지 페이지는 이 구성 요소들을 통신 프로토콜, 통신 모델, HMI, 네트워크 지연/QoS, 로봇 프로그래밍 방식 관점에서 각각 다룬다
