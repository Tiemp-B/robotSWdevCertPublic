# Summary

원격제어 시스템에서 **[[WebSocket]]**을 사용하는 근본적인 이유는 클라이언트가 보는 로봇 상태와 로봇의 실제 상태를 지속적으로 일치시키는 **[[상태 동기화(State Synchronization)|상태 동기화]]**에 있다. 폴링(Polling)이 매 순간 상태를 "질문"해서 알아내는 방식이라면, WebSocket은 상태가 실제로 바뀔 때마다 서버가 즉시 밀어주므로 어긋난 상태(Stale State)를 보게 될 위험이 구조적으로 줄어든다.

# Notes

<aside>상태 동기화(State Synchronization) 문제</aside>

클라이언트가 마지막으로 알고 있는 로봇 상태와 로봇의 실제 현재 상태 사이에는 항상 어느 정도의 시간차가 존재할 수 있다. 이 간극을 얼마나 줄이느냐가 원격제어 시스템 설계의 핵심 과제다.

<aside>폴링 방식의 상태 동기화 한계</aside>

폴링은 클라이언트가 주기적으로 "지금 상태가 어떤가"를 물어보는 방식이다. 폴링 주기 사이에 상태가 바뀌면, 클라이언트는 다음 폴링 시점까지 낡은(Stale) 상태를 계속 보고 있게 된다. 폴링 주기를 줄이면 최신성은 높아지지만 불필요한 요청이 그만큼 늘어난다.

<aside>WebSocket을 사용하는 주된 이유</aside>

"로봇 원격제어 시스템에서 WebSocket을 사용하는 주된 이유로 가장 적절한 것"은 **서버가 상태 변화 시점에 즉시 클라이언트에 알려(Push), 클라이언트의 상태를 실제 로봇 상태와 지속적으로 일치시킬 수 있다는 점**이다. 단순히 "속도가 빠르다"거나 "가볍다"는 것이 핵심이 아니라, 폴링 없이도 최신 상태를 유지할 수 있다는 **동기화 관점의 이유**가 핵심이다.

<aside>WebSocket 프로토콜 자체의 특징</aside>

지속 연결, 서버 푸시, HTTP 업그레이드 핸드셰이크 같은 프로토콜 자체의 세부 특징은 [[2. MQTT·WebSocket과 실시간 모니터링 통신]]과 [[4. WebSocket과 실시간 통신]]에서 이미 다뤘으므로 여기서는 반복하지 않는다.

<aside>상태 동기화 실패 시 나타나는 문제</aside>

클라이언트가 오래된 상태를 최신인 것처럼 신뢰하면, [[6. 통신 예외 처리와 재연결]]에서 다룬 것처럼 운영자가 실제와 다른 상태를 근거로 잘못된 판단을 내릴 위험이 있다. 상태 동기화는 "한 번 맞춰두면 끝"이 아니라, 통신이 끊기거나 예외가 발생할 때마다 다시 위협받는 지속적인 과제다.

<aside>완전한 동기화 보장의 어려움</aside>

WebSocket을 쓰더라도 네트워크 지연이 0이 아닌 이상, 클라이언트가 보는 상태는 항상 로봇의 "아주 약간 과거" 상태일 수밖에 없다. 완벽한 실시간 동기화는 불가능하며, 결국 이 지연을 얼마나 줄이느냐의 문제로 귀결된다([[5. 네트워크 지연과 QoS]] 참고).

<aside>재연결 시 놓친 상태 복구 — 시퀀스 번호</aside>

연결이 끊겼다 재연결되면, 그 사이 발생한 상태 변화를 어떻게 따라잡을지가 문제가 된다. 실무에서는 **서버가 메시지마다 단조증가하는 시퀀스 번호를 부여**하고, 클라이언트가 마지막으로 받은 번호를 기억해 두었다가 재연결 시 그 번호를 서버에 전달해 **그 이후 놓친 메시지만 재전송**받는 방식을 쓴다. 이를 위해 서버는 최근 메시지를 일정 기간 버퍼링해 둔다.

<aside>연결은 됐지만 죽은 상태 감지 — 하트비트</aside>

TCP 연결 자체는 "연결됨"으로 표시되지만 상대가 실제로는 응답하지 못하는 **좀비 연결**이 있을 수 있다. **[[하트비트(Heartbeat)|하트비트]]**(주기적 Ping/Pong)로 이런 상태를 감지해, 응답이 없으면 재연결을 시도한다. "TCP 연결이 유지되고 있으면 응용 계층 통신도 항상 정상이다"라는 서술은 오답이다 — 하트비트가 필요한 이유가 바로 이 가정이 항상 성립하지는 않기 때문이다.

<aside>예시 — 로봇 위치 상태 동기화</aside>

**예시**: 로봇이 이동 중일 때 WebSocket으로 위치가 바뀔 때마다 즉시 클라이언트에 전송되면, 대시보드의 로봇 아이콘 위치가 실제 로봇 위치와 거의 실시간으로 일치하게 유지된다. 폴링 방식이었다면 폴링 주기 사이의 움직임은 화면에 반영되지 않다가, 다음 폴링 시점에 갑자기 "점프"하는 것처럼 보였을 것이다.

---

<aside>핵심 정리</aside>

- 원격제어에서 WebSocket을 쓰는 주된 이유는 **속도나 경량성이 아니라, 서버 푸시를 통한 지속적인 상태 동기화**에 있다
- 폴링은 주기 사이의 상태 변화를 놓쳐 낡은 상태를 보여줄 수 있지만, WebSocket은 변화 시점에 즉시 반영한다
- 네트워크 지연이 0이 아닌 이상 완벽한 실시간 동기화는 불가능하며, 통신 예외 발생 시 동기화는 다시 깨질 수 있다
- 재연결 시에는 시퀀스 번호로 놓친 메시지만 복구하고, 하트비트로 좀비 연결(연결은 유지되지만 응답 없는 상태)을 감지한다
