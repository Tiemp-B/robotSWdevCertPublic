# Summary

로봇의 센서 값은 "시각 + 값"이 끊임없이 쌓이는 형태다. 이런 데이터에 특화된 것이 **[[시계열 데이터베이스(Time Series Database)|시계열 데이터베이스]]**이며, 로그처럼 정형화되지 않은 대량의 데이터는 **[[NoSQL]]** 데이터베이스로 저장하는 경우가 많다.

# Notes

<aside>시계열 데이터베이스(Time Series Database)</aside>

시간 순서대로 계속 기록되는 데이터(센서 값, 배터리 잔량, 위치 등)를 저장·조회하는 데 최적화된 데이터베이스다.

- 데이터가 대부분 **추가(append)** 위주로 들어오고, 이미 저장된 값을 수정하는 경우는 드물다
- 시간 범위를 기준으로 한 조회(예: "지난 1시간 동안의 평균 온도")가 매우 빈번하고 빨라야 한다
- 오래된 데이터는 요약해 압축하거나 자동으로 삭제하는 **보존 정책(retention policy)**을 흔히 사용한다

"시계열 데이터베이스는 이미 저장된 과거 값을 자주 수정하는 워크로드에 최적화되어 있다"는 서술은 시계열 데이터의 append 위주 특성과 반대되는 오답이다.

<aside>다운샘플링(Downsampling)과 롤업 — 보존 정책의 실제 구현</aside>

"오래된 데이터를 요약해 압축한다"는 것은 구체적으로 **다운샘플링(Downsampling)** 을 뜻한다. 세밀한 원본 데이터(예: 1초 단위)에 평균·최댓값 같은 집계 함수를 적용해, 더 성긴 간격(예: 1시간 단위)의 요약 데이터인 **롤업(Rollup)** 을 만드는 것이다. 최근 데이터는 원본 그대로 정밀하게 보관하고, 오래된 데이터는 롤업만 남겨 저장 공간을 줄이면서도 장기 추세 분석은 계속 가능하게 하는 전략이 흔히 쓰인다.

<aside>NoSQL 데이터베이스</aside>

관계형 데이터베이스(RDB)의 고정된 테이블 스키마 대신, 유연한 구조로 대량의 데이터를 저장하는 데이터베이스를 통칭한다.

| NoSQL 유형 | 저장 방식 | 특징 |
|---|---|---|
| 키-값(Key-Value) | 키 하나에 값 하나를 대응 | 구조가 가장 단순해 **매우 높은 확장성·성능**을 낼 수 있음 |
| 문서(Document) | JSON 등 문서 단위로 저장 | 필드 구조가 유연해 로그처럼 형태가 조금씩 다른 데이터에 적합 |
| 컬럼(Column-family) | 컬럼 단위로 묶어 저장 | 매우 큰 규모의 데이터를 분산 저장하는 데 적합 |
| 그래프(Graph) | 노드와 관계(엣지)로 저장 | 로봇 간 관계, 지도 연결 관계처럼 관계 자체가 중요한 데이터에 적합 |

"키-값 쌍으로 데이터를 저장하며 높은 확장성과 성능을 제공하는 NoSQL 유형"은 **키-값(Key-Value) 스토어**를 가리킨다.

<aside>왜 로봇 데이터에 NoSQL/시계열 DB를 쓰는가</aside>

로봇 다수가 매초 쏟아내는 센서·로그 데이터는 양이 방대하고 형태도 조금씩 다를 수 있어, 고정된 테이블 스키마의 RDB보다 **유연하고 수평 확장이 쉬운** NoSQL/시계열 DB가 적합한 경우가 많다.

<aside>예시 — 로봇 플릿의 데이터 저장 구성</aside>

**예시**: 수십 대 로봇의 배터리·위치 값은 시계열 데이터베이스에 초 단위로 쌓이고, 각 로봇의 동작 로그(형태가 조금씩 다른 이벤트 메시지)는 키-값 또는 문서형 NoSQL에 저장해, 나중에 로봇 ID로 빠르게 조회할 수 있도록 구성한다.

---

<aside>핵심 정리</aside>

- 시계열 데이터베이스는 추가(append) 위주의 시간순 데이터 저장·조회에 최적화되어 있다
- 다운샘플링(롤업)으로 오래된 데이터를 성긴 간격의 요약값으로 압축해 저장 공간을 절약하면서도 장기 추세는 유지할 수 있다
- NoSQL은 키-값·문서·컬럼·그래프 등 유연한 구조를 제공하며, 키-값 스토어는 그중 가장 단순하고 확장성·성능이 높다
- 로봇처럼 대량·다양한 형태의 데이터를 다룰 때는 고정 스키마의 RDB보다 NoSQL/시계열 DB가 적합한 경우가 많다
