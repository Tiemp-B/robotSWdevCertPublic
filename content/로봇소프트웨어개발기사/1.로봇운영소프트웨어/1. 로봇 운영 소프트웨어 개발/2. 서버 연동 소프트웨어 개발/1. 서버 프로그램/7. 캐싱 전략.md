# Summary

**캐싱(Caching)**은 자주 조회되지만 자주 변경되지는 않는 데이터를 DB보다 빠른 저장소(주로 메모리)에 미리 저장해 응답 속도를 높이고 DB 부하를 줄이는 기법이다. 캐시는 서버 로컬에 둘 수도, 여러 서버가 공유하는 분산 캐시로 둘 수도 있으며, 원본과의 불일치를 막기 위한 무효화 전략이 반드시 함께 필요하다.

# Notes

<aside>캐싱의 목적</aside>

DB 조회나 연산 결과처럼 비용이 큰 작업의 결과를 빠른 저장소에 임시 보관해 두었다가 동일 요청이 다시 오면 재사용한다. 목적은 **응답 시간 단축**과 **DB(원본 자원) 부하 감소** 두 가지다.

<aside>로컬 캐시 vs 분산 캐시</aside>

| 항목 | 로컬 캐시 | 분산 캐시 |
|---|---|---|
| 위치 | 서버 프로세스 자체 메모리 | Redis 등 별도 공유 캐시 서버 |
| 속도 | 매우 빠름 | 로컬보다 느리지만 DB보다 빠름 |
| 다중 서버 환경 | 서버마다 캐시 내용이 달라질 수 있음 | 여러 서버가 동일한 캐시를 공유 |

서버가 여러 대로 [[5. 로드밸런싱과 확장성|수평 확장]]된 환경에서는 로컬 캐시만 쓰면 서버마다 캐시 내용이 어긋나는 문제가 커지므로, 분산 캐시가 더 적합해진다.

<aside>캐시 무효화(쓰기) 전략</aside>

| 전략 | 동작 |
|---|---|
| Cache-Aside(지연 로딩) | 조회 시 캐시에 없으면 DB를 조회해 캐시에 채우고, 데이터 변경 시 캐시를 지움 — **가장 흔히 쓰이는 방식** |
| Write-Through | 데이터 변경 시 캐시와 DB를 **동시에(동기적으로)** 갱신 — 캐시가 항상 최신 상태 유지 |
| Write-Behind(Write-Back) | 캐시를 먼저 갱신하고, 지연된 시점에 비동기로 DB에 반영 — 쓰기 속도는 빠르지만 캐시 장애 시 미반영 데이터 유실 위험 |
| TTL(Time-To-Live) | 일정 시간이 지나면 캐시가 자동 만료 |

<aside>캐시로 인한 데이터 불일치</aside>

"캐시를 사용하면 항상 최신 데이터를 보장할 수 있다"는 서술은 옳지 않다. 캐시는 본질적으로 원본과 일시적으로 어긋날 수 있는 가능성(Stale Data)을 내포하며, **캐시 무효화 전략을 얼마나 촘촘하게 설계하느냐가 이 불일치를 얼마나 줄이느냐를 결정**한다.

<aside>캐싱과 커넥션 풀/확장성의 관계</aside>

[[4. DB 연동과 트랜잭션]]에서 다룬 커넥션 풀이 "연결을 재사용해 연결 비용을 줄이는" 접근이라면, 캐싱은 한 걸음 더 나아가 **DB 접근 자체를 생략**해 부하를 줄이는 접근이다. 두 기법은 배타적이지 않고 함께 적용되는 경우가 많다.

<aside>예시 — 로봇 설정값 조회 캐싱</aside>

**예시**: 로봇 기종별 기본 제어 파라미터처럼 자주 조회되지만 거의 변경되지 않는 데이터는 분산 캐시에 저장해 두고, 관리자가 값을 변경할 때만 Write-Through 방식으로 캐시를 갱신한다. 이렇게 하면 수십 대 로봇이 동시에 설정값을 요청해도 매번 DB를 조회하지 않고 캐시에서 즉시 응답할 수 있다.

---

<aside>핵심 정리</aside>

- 캐싱의 목적은 **응답 속도 향상과 DB 부하 감소** — 로컬/분산 캐시는 다중 서버 환경에서의 일관성 여부로 갈림
- 무효화 전략: **Cache-Aside**(가장 흔함, 지연 로딩) / **Write-Through**(동기 갱신) / **Write-Behind**(비동기 갱신, 유실 위험)
- 캐시는 항상 최신 데이터를 보장하지 않으며, 이 불일치 관리가 캐싱 설계의 핵심 과제
- 커넥션 풀(연결 재사용)과 캐싱(DB 접근 생략)은 함께 쓰이는 보완적 기법
