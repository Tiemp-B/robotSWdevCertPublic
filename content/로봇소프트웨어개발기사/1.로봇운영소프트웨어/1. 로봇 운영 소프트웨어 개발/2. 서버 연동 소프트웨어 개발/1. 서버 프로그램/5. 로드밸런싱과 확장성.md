# Summary

**[[로드밸런싱(Load Balancing)|로드밸런싱]]**은 다수의 서버 인스턴스에 요청을 분산시켜 특정 서버에 부하가 집중되지 않도록 하는 기법으로, 목적은 개별 서버 하나의 성능을 극대화하는 것이 아니라 **여러 서버에 걸친 부하 분산으로 전체 가용성과 처리량을 높이는 것**이다. 서버 확장에는 개별 서버 성능을 높이는 수직적 확장과 서버 대수를 늘리는 수평적 확장이 있으며, 로드밸런싱은 수평적 확장의 전제조건이다.

# Notes

<aside>로드밸런싱의 목적</aside>

- 특정 서버로 요청이 몰려 과부하가 걸리는 것을 방지하고 여러 서버에 고르게 분산
- 한 서버가 장애로 멈춰도 나머지 서버가 이어받아 **가용성(Availability)** 향상
- 여러 서버가 나눠 처리해 전체 **처리량(Throughput)** 증가

"로드밸런싱의 목적은 한 서버의 성능을 극대화하는 것"이라는 서술은 틀렸다 — 로드밸런싱의 핵심은 개별 서버 성능 향상이 아니라 **다수 서버에 걸친 균형 분산**이다.

<aside>로드밸런싱 알고리즘</aside>

| 알고리즘 | 방식 |
|---|---|
| 라운드 로빈(Round Robin) | 서버들에 순서대로 요청을 배정 |
| 최소 연결(Least Connections) | 현재 연결(부하) 수가 가장 적은 서버로 배정 |
| IP 해시(IP Hash) | 클라이언트 IP를 기준으로 항상 같은 서버로 배정 |

<aside>수직적 확장 vs 수평적 확장</aside>

| 항목 | 수직적 확장(Scale-up) | 수평적 확장(Scale-out) |
|---|---|---|
| 방법 | 서버 한 대의 사양을 높임 | 서버 대수를 늘림 |
| 한계 | 하드웨어 성능의 물리적 한계 존재 | 이론상 계속 추가해 확장 가능 |
| 부가 요구사항 | 별도 없음 | 로드밸런싱, 여러 서버 간 상태 공유 필요 |

<aside>스티키 세션(Sticky Session)</aside>

[[3. 세션과 상태 관리]]에서 예고한 문제 — 서버가 여러 대로 늘어나면 같은 클라이언트의 요청이 매번 다른 서버로 갈 수 있어, 특정 서버 메모리에만 저장된 세션을 찾지 못하는 문제가 생긴다. **[[스티키 세션(Sticky Session)|스티키 세션]]**은 로드밸런서가 같은 클라이언트의 요청을 항상 같은 서버로 보내도록 고정하는 방식이다.

- 장점: 기존 서버 메모리 기반 세션 저장 방식을 그대로 사용 가능
- 단점: 특정 서버에 부하가 쏠릴 수 있고, 그 서버가 죽으면 세션도 함께 소실
- 근본적인 대안은 분산 캐시(Redis 등)로 세션 저장소 자체를 공유하는 것

<aside>헬스 체크(Health Check)</aside>

로드밸런서는 주기적으로 각 서버의 생존 여부를 확인해, 응답하지 않는 서버를 자동으로 라우팅 대상에서 제외한다 — 장애 서버로 요청이 계속 전달되는 것을 막는다.

<aside>예시 — 로봇 관제 서버의 수평 확장</aside>

**예시**: 로봇 대수가 늘어나 관제 서버 한 대로는 [[2. 동시성 처리 모델|C10K 수준의 연결]]을 감당하기 어려워지면, 서버를 여러 대로 늘리고 로드밸런서가 라운드 로빈으로 연결을 분산한다. 이때 세션은 서버 메모리 대신 Redis 같은 분산 캐시에 저장해, 어느 서버가 요청을 받든 동일한 로그인 상태를 인식하도록 구성하는 것이 스티키 세션보다 근본적인 해결책이다.

---

<aside>핵심 정리</aside>

- 로드밸런싱의 목적은 **다수 서버에 걸친 부하 분산으로 가용성·처리량을 높이는 것**(개별 서버 성능 극대화 아님)
- 수직적 확장(성능 향상)과 수평적 확장(대수 증가)은 다른 접근이며, 수평적 확장엔 로드밸런싱+상태 공유가 필요
- 스티키 세션은 임시방편, 분산 캐시를 통한 세션 공유가 더 근본적인 해결책
