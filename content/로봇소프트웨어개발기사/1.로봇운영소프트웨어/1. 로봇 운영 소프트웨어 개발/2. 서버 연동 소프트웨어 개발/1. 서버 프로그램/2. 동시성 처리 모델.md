# Summary

서버가 다수의 클라이언트 요청을 동시에 처리하는 방식에는 **프로세스 기반, 스레드 기반, 이벤트 기반(비동기 I/O)** 세 가지 모델이 있다. 접속자 수가 급증하면 프로세스/스레드 기반 모델은 메모리·컨텍스트 스위칭 오버헤드로 한계에 부딪히는데, 이를 **C10K 문제**라 하며, 이를 해결하기 위해 등장한 것이 이벤트 기반 비동기 처리 방식이다.

# Notes

<aside>동시성과 병렬성</aside>

- **동시성(Concurrency)**: 여러 작업을 번갈아 진행해 마치 동시에 처리되는 것처럼 보이게 함 — 단일 코어에서도 가능
- **병렬성(Parallelism)**: 여러 작업을 물리적으로 동시에 실행 — 멀티코어/멀티프로세서 필요

서버가 "다수 요청을 동시에 처리한다"는 것이 반드시 물리적 병렬 실행을 의미하지는 않는다 — 단일 코어에서도 빠르게 번갈아 처리하는 동시성만으로 다수 클라이언트를 응대할 수 있다.

<aside>프로세스/스레드 기반 모델</aside>

- **프로세스 기반**: 연결마다 새 프로세스를 fork — 한 프로세스가 죽어도 다른 프로세스에 영향 없는 격리성이 장점이지만, 생성 비용·메모리 사용량이 커 연결이 많아지면 비효율적
- **스레드 기반(Thread-per-Connection)**: 연결마다 스레드를 생성 — 프로세스보다 가볍지만 연결이 수천 개로 늘면 메모리 소비와 컨텍스트 스위칭 비용이 급격히 증가

<aside>C10K 문제</aside>

1999년 Dan Kegel이 제기한 문제로, 동시 접속 클라이언트가 **1만(10,000)** 수준에 이르면 연결 하나당 프로세스/스레드를 할당하는 방식으로는 메모리 고갈과 과도한 컨텍스트 스위칭으로 서버가 감당하지 못하게 되는 현상을 말한다("Concurrent 10,000 connections"에서 이름 유래).

<aside>이벤트 기반 비동기 처리(Event-Driven Async I/O)</aside>

연결마다 스레드를 할당하는 대신, **단일(또는 소수의) 스레드**가 [[이벤트 루프(Event Loop)|이벤트 루프]]를 돌며 I/O가 준비된 연결만 골라 처리한다.

- I/O 작업 완료를 기다리며 스레드를 블로킹하지 않는다(논블로킹 I/O)
- 적은 수의 스레드로도 수만 개의 연결을 유지할 수 있어 **C10K 문제의 표준 해법**(Nginx의 epoll 기반 이벤트 루프, Node.js 등)으로 자리잡았다
- "이벤트 기반 방식은 연결마다 별도 스레드를 생성한다"는 서술은 스레드 기반 모델과 혼동한 오답이다 — 핵심은 **스레드 수를 늘리지 않고도** 다수 연결을 처리하는 데 있다

<aside>세 모델 비교</aside>

| 항목 | 프로세스 기반 | 스레드 기반 | 이벤트 기반(비동기) |
|---|---|---|---|
| 연결당 자원 | 프로세스 1개 | 스레드 1개 | 스레드 소비 없음 |
| 메모리 사용량 | 매우 큼 | 큼 | 작음 |
| C10K 대응력 | 낮음 | 낮음~중간 | 높음 |
| 대표 사례 | Apache(prefork) | 다수의 전통적 WAS | Node.js, Nginx |

<aside>예시 — 로봇 플릿 상태 스트림 수신 서버</aside>

**예시**: 수천 대의 로봇이 끊임없이 상태를 보고하는 관제 서버를 연결마다 스레드를 생성하는 방식으로 구현하면 로봇 대수가 늘어날수록 C10K 문제에 부딪힌다. 이벤트 기반 비동기 I/O 모델로 구현하면 적은 리소스로도 훨씬 많은 로봇 연결을 동시에 유지할 수 있다 — [[2. MQTT·WebSocket과 실시간 모니터링 통신]]에서 다룬 다수 로봇의 실시간 통신을 받아내는 서버 쪽 구현이 이 문제와 직결된다.

<aside>핵심 정리</aside>

- 동시성(번갈아 처리)과 병렬성(물리적 동시 실행)은 다른 개념
- 프로세스/스레드 기반 모델은 연결마다 자원을 할당해 **C10K 문제**(1999, Dan Kegel)에 취약
- 이벤트 기반 비동기 처리는 **적은 스레드로 다수 연결을 논블로킹 I/O로 처리**해 C10K를 해결
