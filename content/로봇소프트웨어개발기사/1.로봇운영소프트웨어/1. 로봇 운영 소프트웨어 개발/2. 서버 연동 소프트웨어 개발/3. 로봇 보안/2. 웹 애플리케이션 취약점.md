# Summary

웹 애플리케이션 보안에서 가장 널리 알려진 두 취약점이 **[[SQL Injection]]**과 **[[XSS(Cross-Site Scripting)|XSS]]**다(둘 다 OWASP가 오래 강조해 온 대표 취약점). SQL Injection은 사용자 입력값에 악의적인 SQL 구문을 끼워 넣어 데이터베이스를 조작하는 공격이고, XSS는 악성 스크립트를 웹페이지에 주입해 다른 사용자의 브라우저에서 실행시키는 공격이다. 이 외에도 **[[CSRF(Cross-Site Request Forgery)|CSRF]]**, **[[Command Injection]]**, **[[인증 취약점(Broken Authentication)]]** 등이 대표적인 웹 애플리케이션 취약점으로 다뤄진다. 이들 모두 **"사용자 입력을 코드가 아니라 데이터로만 취급한다"**는 공통 원칙으로 방어된다.

# Notes

<aside>SQL Injection 개념</aside>

사용자 입력값을 SQL 쿼리 문자열에 그대로 이어붙일 때, 입력값 안에 SQL 구문을 삽입해 원래 의도하지 않은 쿼리가 실행되게 만드는 공격이다. 예를 들어 로그인 폼의 비밀번호 칸에 `' OR '1'='1`을 입력해 조건절을 항상 참으로 만들어 인증을 우회하는 방식이 대표적이다.

<aside>SQL Injection 방지 — Prepared Statement</aside>

OWASP가 명시하는 **가장 효과적인 방어책은 [[Prepared Statement(매개변수화된 쿼리)|Prepared Statement]](매개변수화된 쿼리)**다. 쿼리의 구조(SQL 코드)와 입력값(데이터)을 분리해 전달하므로, 입력값에 어떤 문자열이 들어와도 SQL 코드로 해석되지 않는다 — 이 방식만으로 SQL Injection 취약점의 대다수가 원천 차단된다. 특수문자를 하나하나 걸러내는 단순 문자열 이스케이프나 블랙리스트 필터링은 우회 가능성이 남아 있어 보조 수단일 뿐 근본적인 해결책이 되지 못한다.

<aside>XSS(Cross-Site Scripting) 개념</aside>

공격자가 게시글·댓글 등 웹페이지에 악성 스크립트를 삽입해 두면, 다른 사용자가 그 페이지를 열람할 때 그 사용자의 브라우저에서 스크립트가 실행되는 공격이다. 이렇게 실행된 스크립트는 [[5. 쿠키(Cookie) 기반 세션 관리|세션 쿠키]]를 탈취하는 등에 악용될 수 있다 — 쿠키에 `HttpOnly` 속성이 필요한 이유가 바로 이 XSS로부터 쿠키 값을 보호하기 위해서다.

<aside>XSS 방지 — 출력 인코딩이 1차 방어</aside>

OWASP 기준으로 **컨텍스트에 맞는 출력 인코딩(Output Encoding)**이 XSS의 1차 방어책이다. 사용자가 입력한 내용을 HTML에 그대로 출력하지 않고 `<`, `>`, `&` 같은 특수문자를 이스케이프 처리해, 브라우저가 이를 스크립트가 아닌 순수 텍스트로 해석하게 만드는 것이 핵심이다. **CSP(Content Security Policy)**는 이를 대체하는 게 아니라 보완하는 **심층 방어(defense-in-depth) 계층**으로 함께 적용된다 — 대부분의 XSS는 입력 검증 누락이 아니라 출력 인코딩 누락에서 비롯된다.

<aside>CSRF(Cross-Site Request Forgery)</aside>

**개념**: 사용자가 로그인된 상태를 이용해, 공격자가 만든 페이지가 사용자 모르게 정상 서버로 요청을 보내도록 속이는 공격이다. XSS가 "악성 스크립트를 실행"시키는 것이라면, CSRF는 스크립트 실행 없이 **이미 인증된 사용자의 권한으로 위조된 요청 자체**를 보내게 만든다는 점이 다르다.

**방지**: 요청마다 예측 불가능한 **CSRF 토큰**을 발급해 서버가 검증하거나, 쿠키의 `SameSite` 속성으로 다른 사이트에서의 요청에는 쿠키가 자동 전송되지 않게 막는 것이 기본 대응책이다.

<aside>Command Injection(OS 커맨드 인젝션)</aside>

**개념**: 사용자 입력값이 검증 없이 OS 셸 명령어의 일부로 실행되어, 공격자가 임의의 시스템 명령을 실행할 수 있게 되는 공격이다. SQL 대신 OS 명령이 대상이라는 점만 다를 뿐, "입력값이 코드로 해석된다"는 원리는 SQL Injection과 동일하다.

**방지**: 사용자 입력을 셸 명령 문자열에 직접 결합하지 않고, 인자를 분리해 전달하는 API를 사용하거나 허용된 명령·문자만 통과시키는 화이트리스트 검증이 기본 대응책이다.

<aside>인증 취약점(Broken Authentication)</aside>

**개념**: 로그인·세션 관리 과정의 허점을 이용해 공격자가 정당한 사용자로 위장하는 취약점이다. 약한 비밀번호 정책, 세션 ID가 URL에 노출되는 경우, 로그아웃 후에도 세션이 만료되지 않는 경우 등이 대표적인 원인이며, SQL Injection·XSS처럼 입력값을 조작하는 공격이 아니라 **인증·세션 관리 절차 자체의 설계 결함**이라는 점이 다르다.

**방지**: 강력한 비밀번호 정책과 다중 인증(MFA) 적용, 세션 ID를 URL이 아닌 쿠키(HttpOnly)로 관리, 일정 시간 미사용 시 세션 자동 만료 등이 기본 대응책이다.

<aside>공통 원칙 — 입력값을 신뢰하지 않는다</aside>

SQL Injection과 XSS는 공격 대상(DB vs 브라우저)이 다르지만, **"사용자로부터 온 데이터는 그 자체로 코드가 아니라 순수한 데이터로만 다뤄야 한다"**는 동일한 원칙으로 방어된다는 공통점이 있다.

<aside>예시 — 로봇 설정 검색 폼에서의 SQL Injection 시도</aside>

**예시**: 관제 대시보드의 로봇 검색창에 로봇 이름 대신 `'; DROP TABLE robots; --` 같은 문자열을 입력했을 때, 쿼리가 문자열을 그대로 이어붙이는 방식이라면 실제로 테이블이 삭제될 수 있다. Prepared Statement를 사용하면 이 입력값은 그저 "존재하지 않는 로봇 이름"으로만 처리되어 안전하다.

<aside>핵심 정리</aside>

- SQL Injection의 1차 방어는 **Prepared Statement(매개변수화된 쿼리)** — 문자열 이스케이프·블랙리스트는 보조 수단일 뿐
- XSS의 1차 방어는 **출력 인코딩**, CSP는 이를 보완하는 심층 방어 계층
- CSRF는 XSS와 달리 스크립트 실행 없이 인증된 권한으로 요청 자체를 위조 — CSRF 토큰·SameSite 쿠키로 방어
- Command Injection은 SQL Injection과 원리는 같고 대상(OS 명령)만 다름
- 인증 취약점은 입력값 조작이 아니라 인증·세션 관리 절차 자체의 설계 결함
- 이 모두 "사용자 입력은 데이터일 뿐 코드가 아니다"라는 원칙으로 방어
