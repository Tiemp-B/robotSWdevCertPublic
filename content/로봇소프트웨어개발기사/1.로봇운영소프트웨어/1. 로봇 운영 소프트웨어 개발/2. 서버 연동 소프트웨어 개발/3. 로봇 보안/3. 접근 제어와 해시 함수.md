# Summary

**[[접근 제어(Access Control)|접근 제어]]**는 [[1. 보안 기본 개념|인가(Authorization)]]를 실제로 구현하는 메커니즘으로, 최소 권한 원칙 등 여러 설계 고려사항을 따른다. **[[해시 함수(Hash Function)|해시 함수]]**는 원래 데이터의 **무결성을 검증**하는 것이 주된 용도이며, 비밀번호를 안전하게 저장하는 것은 이 성질을 응용한 실무적 활용 사례다.

# Notes

<aside>접근 제어 개념과 모델</aside>

인가(Authorization)를 실제 시스템에 구현한 것으로, "누가 어떤 자원에 어떤 작업을 할 수 있는가"를 규칙으로 정의하고 강제하는 메커니즘이다.

| 모델 | 방식 |
|---|---|
| RBAC(Role-Based Access Control) | 사용자에게 역할(관리자/운영자 등)을 부여하고, 역할별로 권한 관리 |
| ABAC(Attribute-Based Access Control) | 사용자·자원·환경의 속성(부서, 시간대 등)을 조합해 동적으로 권한 판단 |

<aside>접근 제어 설계 원칙</aside>

- **최소 권한 원칙(Principle of Least Privilege)**: 각 사용자에게 작업에 필요한 최소한의 권한만 부여
- **기본 거부(Default Deny)**: 명시적으로 허용되지 않은 접근은 기본적으로 차단
- **권한 회수의 용이성**: 역할 변경·퇴사 시 권한을 신속히 회수할 수 있어야 함
- **감사 로그**: 누가 언제 어떤 자원에 접근했는지 기록해 사후 추적 가능하게 함

"모든 사용자에게 기본적으로 넓은 권한을 부여하고 필요할 때만 제한한다"는 서술은 접근 제어 설계 원칙에 부합하지 않는다 — 기본은 **최소 권한·기본 거부**여야 한다.

<aside>해시 함수의 성질</aside>

임의 길이의 입력을 고정 길이의 출력(해시값)으로 변환하는 함수로, 세 가지 성질을 갖는다.

- **결정성(Deterministic)**: 같은 입력은 항상 같은 출력을 냄
- **눈사태 효과(Avalanche Effect)**: 입력이 조금만 달라져도 출력은 (대략 절반가량의 비트가 바뀔 만큼) 크게 달라짐
- **단방향성(One-way / 역상 저항성)**: 출력값으로부터 원래 입력을 역산하기 어려움

<aside>해시 함수의 주요 용도 — 무결성 검증</aside>

해시 함수의 **1차 용도는 데이터가 전송·저장 중에 변조되지 않았는지 확인하는 무결성 검증**이다. 원본의 해시값과, 수신 측에서 데이터를 받아 다시 계산한 해시값을 비교해 일치하면 변조되지 않았다고 판단한다.

<aside>2차 응용 — 비밀번호 저장과 솔트</aside>

해시 함수의 단방향성을 응용해, 비밀번호를 평문으로 저장하지 않고 해시값으로 저장하는 데도 널리 쓰인다(무결성 검증에 이은 2차적 실무 응용). 이때는 동일한 비밀번호가 항상 같은 해시값을 낸다는 점을 악용하는 **레인보우 테이블 공격**(사전에 계산해 둔 해시값 테이블과 대조하는 공격)을 막기 위해, 비밀번호마다 임의의 값(**솔트, Salt**)을 더해 해시하는 것이 실무 표준이다.

<aside>예시 — 로봇 설정 파일의 무결성 검증</aside>

**예시**: 로봇에 배포되는 펌웨어나 설정 파일을 내려받을 때, 배포 서버가 해당 파일의 해시값을 함께 제공한다. 로봇은 파일을 받은 후 직접 해시값을 계산해 제공받은 값과 비교함으로써, 전송 중 변조나 손상 여부를 확인할 수 있다.

<aside>핵심 정리</aside>

- 접근 제어는 인가를 구현하는 메커니즘이며, **최소 권한 원칙·기본 거부**가 핵심 설계 원칙
- 해시 함수 성질: 결정성·눈사태 효과·단방향성 / **1차 용도는 무결성 검증**, 비밀번호 저장은 2차 응용
- 비밀번호 해시 저장 시 레인보우 테이블 공격을 막기 위해 **솔트**를 함께 사용
