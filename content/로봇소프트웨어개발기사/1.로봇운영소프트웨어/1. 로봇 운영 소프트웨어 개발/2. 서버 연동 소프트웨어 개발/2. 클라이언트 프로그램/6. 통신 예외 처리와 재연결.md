# Summary

클라이언트 프로그램은 서버와의 통신 중 타임아웃, 연결 끊김, 서버 오류 등 다양한 예외 상황에 대비해야 한다. 예외를 적절히 처리하지 않으면 클라이언트가 무한정 대기하거나, 사용자가 오류를 인지하지 못한 채 **오래된 상태 정보를 최신인 것처럼 신뢰하게 되는 동기화 문제**가 생길 수 있다.

# Notes

<aside>통신 중 발생할 수 있는 예외 유형</aside>

| 유형 | 설명 |
|---|---|
| 타임아웃(Timeout) | 요청에 대한 응답이 일정 시간 내 오지 않음 |
| 연결 끊김 | 네트워크 단절, WebSocket 연결 종료 등 |
| 서버 오류 응답(5xx) | 서버 내부에서 처리 중 오류 발생 |
| 클라이언트 오류 응답(4xx) | 잘못된 요청(권한 없음, 존재하지 않는 자원 등) |

요청에 타임아웃을 지정하지 않으면 응답 없는 서버를 무한정 기다리게 되어 클라이언트가 멈춘 것처럼 보일 수 있다 — 적절한 타임아웃 값을 설정하고, 타임아웃 발생 시 사용자에게 알리거나 재시도하는 처리가 필요하다.

<aside>재연결과 지수 백오프</aside>

[[4. WebSocket과 실시간 통신|WebSocket]]처럼 지속 연결 방식은 연결이 끊기면 자동으로 다시 연결을 시도하는 로직이 필요하다. 끊기자마자 즉시 재시도를 반복하면 서버에 과도한 부담(재연결 폭주)을 줄 수 있으므로, 재시도 간격을 점점 늘려가는 **[[지수 백오프(Exponential Backoff)|지수 백오프]]** 방식이 업계 표준으로 쓰인다 — 실무에서는 여기에 무작위 지연(jitter)을 더해 다수 클라이언트가 동시에 재연결을 시도하는 상황을 추가로 완화하기도 한다.

<aside>에러 로깅</aside>

예외가 발생했을 때 이를 조용히 무시하지 않고 클라이언트 로그로 남겨 두면 추후 원인 분석에 활용할 수 있다. 서버 측 [[5. 데이터 로깅과 이상치 탐지|데이터 로깅]]이 로봇 상태의 이력을 남기는 것과 마찬가지로, 클라이언트 측에서도 통신 오류 발생 시점과 상황을 기록해 두는 것이 바람직하다.

<aside>동기화 문제를 무시하면 안 되는 이유</aside>

통신 예외로 클라이언트가 알고 있는 상태와 서버(로봇)의 실제 상태가 어긋나는 **동기화 문제**가 생길 수 있다. 이를 무시하면 운영자가 로봇의 실제 상태를 오인해 잘못된 명령(이미 멈춘 로봇에 불필요한 정지 명령을 반복하거나, 반대로 실제 위험 상태를 인지하지 못하는 등)을 내릴 수 있다.

<aside>예시 — 로봇 모니터링 클라이언트의 예외 처리 흐름</aside>

**예시**: 대시보드가 로봇 상태 요청에 3초 내 응답이 없으면 타임아웃으로 처리하고 화면에 "연결 불안정" 배지를 표시한다. WebSocket 연결이 끊기면 지수 백오프로 재연결을 시도하며, 그 사이 화면에는 "마지막 갱신 시각"을 함께 표시해 운영자가 지금 보는 데이터가 얼마나 신선한지 스스로 판단할 수 있게 한다.

---

<aside>핵심 정리</aside>

- 통신 예외에는 타임아웃·연결 끊김·서버 오류·클라이언트 오류 등이 있으며, 각각 적절한 대응이 필요
- 지속 연결이 끊기면 **지수 백오프**(+jitter)로 재연결을 시도해 서버 부담을 줄임
- **오류를 숨기고 오래된 상태를 계속 보여주는 것은 부적절한 처리** — 동기화 문제로 잘못된 로봇 제어 판단을 유발할 수 있음
- 예외는 로그로 남겨 추후 원인 분석에 활용
