# Summary

**[[WebSocket]]**은 하나의 연결을 지속적으로 유지하면서 서버와 클라이언트가 양방향으로 데이터를 주고받을 수 있는 프로토콜이다. 클라이언트 입장에서는 반복적으로 서버에 요청을 보내는 폴링(Polling) 방식보다 적은 오버헤드로 실시간성 높은 갱신을 받을 수 있다는 것이 핵심 장점이다. 프로토콜 자체의 상세(HTTP 폴링·SSE와의 비교표)는 [[2. MQTT·WebSocket과 실시간 모니터링 통신]]에서 이미 다뤘으므로, 여기서는 **클라이언트 프로그램이 이를 채택하는 이유와 구현 관점**에 집중한다.

# Notes

<aside>클라이언트 관점에서 본 WebSocket의 장점</aside>

- **반복 요청 불필요**: 연결을 한 번 맺으면 이후 별도로 요청을 반복하지 않아도 서버가 필요할 때 데이터를 보내준다
- **서버 푸시 수신**: 클라이언트가 먼저 요청하지 않아도 서버가 상태 변화 시점에 즉시 데이터를 밀어준다
- **헤더 오버헤드 감소**: 폴링처럼 매 요청마다 HTTP 헤더를 반복 전송하지 않는다
- **실시간성**: 폴링 주기에 묶이지 않고 변화가 생기는 즉시 데이터를 받는다

<aside>HTTP 폴링과의 체감 차이(클라이언트 코드 관점)</aside>

폴링 방식은 클라이언트 코드가 `setInterval` 등으로 일정 주기마다 요청을 반복 호출해야 하며, 이는 서버 부하와 클라이언트 자원 소모를 동시에 유발한다. WebSocket은 연결 이후 별도의 반복 호출 코드 없이 `onmessage` 콜백 하나만 등록해 두면 서버가 보내는 대로 데이터를 받는다는 점에서 코드 구조 자체가 단순해진다.

<aside>WebSocket 클라이언트 구현 요소</aside>

브라우저의 WebSocket API는 아래 네 가지 이벤트 콜백을 중심으로 구현된다.

| 이벤트 | 시점 |
|---|---|
| onopen | 연결이 성공적으로 수립되었을 때 |
| onmessage | 서버로부터 메시지를 수신했을 때 |
| onclose | 연결이 종료되었을 때 |
| onerror | 통신 중 오류가 발생했을 때 |

<aside>연결 끊김과 재연결 필요성</aside>

WebSocket은 지속 연결이기 때문에 네트워크 문제로 연결이 끊어질 수 있고, 이를 감지해 다시 연결을 맺는 로직이 반드시 필요하다. 재연결 전략(지수 백오프 등)의 상세는 [[6. 통신 예외 처리와 재연결]]에서 다룬다.

<aside>예시 — 로봇 관제 대시보드의 실시간 갱신</aside>

**예시**: 대시보드가 로봇 상태를 1초마다 폴링하는 대신 WebSocket 연결 하나로 전환하면, 클라이언트는 더 이상 초당 반복 요청을 보내지 않고 서버가 실제로 상태가 바뀐 시점에만 메시지를 보내주는 구조가 된다. 이는 클라이언트·서버 양쪽의 불필요한 트래픽을 크게 줄인다.

---

<aside>핵심 정리</aside>

- 클라이언트 관점에서 WebSocket의 핵심 장점은 **반복 요청 없이 서버 푸시를 받을 수 있다는 것**, 헤더 오버헤드도 감소
- 구현은 onopen/onmessage/onclose/onerror 네 가지 이벤트 콜백을 중심으로 이뤄짐
- 지속 연결이므로 끊김에 대비한 재연결 로직이 반드시 필요
