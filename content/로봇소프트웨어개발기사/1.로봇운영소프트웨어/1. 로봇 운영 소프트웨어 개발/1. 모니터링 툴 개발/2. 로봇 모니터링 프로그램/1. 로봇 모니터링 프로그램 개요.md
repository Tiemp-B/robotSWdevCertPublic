# Summary

같은 세부항목의 [[1. 로봇 제어기 |"1. 로봇 제어기 특성"]]이 제어기 **내부**(HW/SW 계층, 실시간성)를 다뤘다면, "로봇 모니터링 프로그램"은 그 제어기가 만들어낸 상태 데이터를 **밖으로 꺼내 사람이 보고 판단할 수 있게 만드는 응용 소프트웨어**를 다룬다. 데이터는 **수집 → 통신 → 저장/처리 → 시각화**의 흐름을 거치며, 이 4단계가 이후 5개 페이지의 뼈대가 된다.

# Notes

<aside>모니터링 프로그램의 데이터 흐름</aside>

로봇 모니터링 프로그램은 대체로 아래 4단계를 거쳐 데이터를 사용자에게 전달한다.

| 단계 | 내용 | 다루는 페이지 |
|---|---|---|
| ① 수집 | 로봇 제어기/센서로부터 상태 데이터 획득 | [[1. 로봇 제어기 \|1. 로봇 제어기 특성]](제어기 내부) |
| ② 통신 | 수집된 데이터를 네트워크로 전달 | [[2. MQTT·WebSocket과 실시간 모니터링 통신]] |
| ③ 저장/처리 | 대규모 현장 통합 감시, 실시간 집계·이상치 판정, 사후 기록 | [[3. SCADA 구조와 산업용 모니터링 시스템]], [[5. 데이터 로깅과 이상치 탐지]], [[6. 스트림 처리(Stream Processing)와 실시간 데이터 파이프라인]] |
| ④ 시각화 | 사람이 보고 판단하도록 화면·알람으로 표현 | [[4. 데이터 시각화와 알람(HMI)]] |

①(수집)은 이미 "1. 로봇 제어기 특성"에서 제어기 내부 관점으로 다뤘으므로 이 세세항목에서는 반복하지 않고, **②~④(통신·처리·시각화)**를 중심으로 다룬다.

<aside>왜 이 순서인가</aside>

- **통신이 처리보다 먼저** 오는 이유: 로봇/현장에서 만들어진 데이터는 물리적으로 떨어진 서버·대시보드로 옮겨져야(통신) 비로소 통합 처리가 가능해진다
- **SCADA(구조)와 스트림 처리(방식)를 함께 배치**한 이유: SCADA가 "여러 현장을 통합 감시하는 계층 구조"를 규정한다면, 스트림 처리는 그 구조 안에서 "데이터가 도착하는 즉시 어떻게 계산할 것인가"라는 실행 방식을 규정한다 — 구조와 실행 방식은 서로 다른 축이므로 별개 페이지로 다룬다
- **로깅과 시각화를 구분**한 이유: 로깅은 "나중에 보려고 기록"하는 사후적 데이터 처리이고, 시각화·알람은 "지금 사람이 보도록" 만드는 표현 계층이다 — 목적이 다르므로 혼동하지 않는다

<aside>이 세세항목에서 다루지 않는 것</aside>

- 제어기 자체의 HW/SW 구성, RTOS·동기화, PID 응답 특성 등은 [[1. 로봇 제어기 |1. 로봇 제어기 특성]] 참고(중복 서술 없음)
- MCU-PC 간 시리얼 통신(RS232C/USART)으로 파라미터를 주고받는 저수준 구현 절차는 [[1. 로봇 제어기 |1. 로봇 제어기 특성]]에서 NCS 필요지식으로 다뤘으므로 반복하지 않는다 — 이 세세항목은 그보다 상위의, 네트워크 기반 모니터링 아키텍처(MQTT/WebSocket/SCADA/HMI/로깅/스트림처리)에 집중한다

---

<aside>핵심 정리</aside>

- 모니터링 프로그램의 데이터 흐름: **수집 → 통신 → 저장/처리 → 시각화**
- 수집(제어기 내부)은 "1. 로봇 제어기 특성"에서 이미 다룸 — 이 세세항목은 **통신·처리·시각화**에 집중
- SCADA(구조)와 스트림 처리(실행 방식)는 서로 다른 축이며, 로깅(사후 기록)과 시각화(즉시 표현)는 목적이 다름
