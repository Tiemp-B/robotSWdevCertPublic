# Summary

[[1. 로봇 모니터링 프로그램 개요|모니터링 데이터 흐름]]의 통신 단계에서 가장 널리 쓰이는 두 프로토콜이 **[[MQTT]]**와 **[[WebSocket]]**이다. MQTT는 다수의 저전력·저대역폭 노드가 브로커를 통해 비동기로 데이터를 발행(publish)하는 구조에 적합하고, WebSocket은 브라우저 대시보드처럼 저지연 양방향 실시간 통신이 필요한 구간에 적합하다 — 경쟁 관계가 아니라 **역할이 다른 상호 보완 구성요소**다.

# Notes

<aside>MQTT — 발행-구독 기반 경량 메시징</aside>

**[[MQTT]]**(Message Queuing Telemetry Transport)는 **[[발행-구독 모델(Publish-Subscribe)|발행-구독(Pub/Sub)]]** 구조의 경량 메시징 프로토콜이다.

- **브로커(Broker)**: 발행자(Publisher)와 구독자(Subscriber)를 중개하는 서버 — 발행자·구독자는 서로를 직접 알 필요가 없다(느슨한 결합)
- **토픽(Topic)**: 메시지를 분류하는 문자열 경로(예: `robot/1/joint_states`) — 구독자는 원하는 토픽을 구독해야 메시지를 받는다
- TCP 기반이며 헤더 오버헤드가 작아 **저대역폭·배터리 제약이 있는 다수의 센서/로봇 노드**가 원격 서버로 텔레메트리를 보내는 용도에 적합하다

<aside>MQTT QoS 3단계</aside>

| QoS | 이름 | 동작 |
|---|---|---|
| 0 | At most once | **한 번만 전송**, 수신 확인(ACK) 없음 — 유실 가능하나 오버헤드 최소 |
| 1 | At least once | 확인이 올 때까지 재전송 — 유실은 없으나 **중복 수신** 가능 |
| 2 | Exactly once | PUBLISH→PUBREC→PUBREL→PUBCOMP **4단계 핸드셰이크**로 정확히 한 번만 전달 |

신뢰도가 높을수록(QoS 2에 가까울수록) 지연·오버헤드가 커지는 트레이드오프이므로, 유실돼도 다음 값으로 대체 가능한 주기적 센서값은 QoS 0~1로, 반드시 전달돼야 하는 알람·명령은 QoS 2로 선택하는 것이 실무적이다 — "한 번만 시도하고 수신 여부를 확인하지 않는" 레벨은 **QoS 0**이다.

<aside>WebSocket — 단일 연결 위의 양방향 통신</aside>

**[[WebSocket]]**은 하나의 TCP 연결 위에서 클라이언트-서버 간 **양방향(Full-Duplex) 실시간 통신**을 제공한다.

- 연결은 HTTP 핸드셰이크(Upgrade 요청)로 시작하지만, 이후에는 HTTP와 독립된 자체 프레임으로 동작
- **지속 연결(Persistent Connection)**을 유지해, 메시지를 주고받을 때마다 매번 새로 연결하거나 헤더 전체를 반복 전송할 필요가 없다
- 서버가 클라이언트의 요청 없이도 먼저 데이터를 보낼 수 있다(**Server Push**) — 매번 클라이언트가 먼저 요청해야 하는 일반 HTTP 요청-응답 모델과의 핵심 차이

<aside>WebSocket vs HTTP 폴링 vs SSE</aside>

| 항목 | HTTP 폴링 | SSE(Server-Sent Events) | WebSocket |
|---|---|---|---|
| 연결 | 매 요청마다 새로 연결 | 최초 1회 연결 후 유지(단일 HTTP) | 최초 1회 연결 후 유지 |
| 방향 | 클라이언트→서버 요청 필수 | **서버→클라이언트 단방향**만 | **양방향(Full-Duplex)** |
| 서버 푸시 | 불가 | 가능(단방향) | 가능(양방향) |
| 지연 | 폴링 주기에 종속 | 이벤트 발생 즉시(단방향) | 이벤트 발생 즉시 |

SSE는 서버→클라이언트로만 데이터를 밀어줄 수 있고 클라이언트가 같은 채널로 되돌려 보낼 수 없다는 점에서 WebSocket과 다르다.

<aside>실무 조합 — 로봇 플릿 모니터링</aside>

**예시**: 수십 대의 이동로봇이 배터리·위치·에러 코드를 5초 주기로 보고할 때는 오버헤드가 작은 **MQTT**로 각 로봇이 브로커에 토픽별로 발행하고, 관제 센터의 **웹 대시보드**는 서버가 그 브로커를 구독한 뒤 다시 **WebSocket**으로 브라우저에 실시간 중계하는 조합이 흔하다. 즉 로봇↔서버 구간은 MQTT, 서버↔브라우저 구간은 WebSocket으로 역할을 분담하는 것이 전형적인 패턴이다.

---

<aside>핵심 정리</aside>

- MQTT = **발행-구독** 경량 프로토콜, 브로커가 중개, QoS 0(최대한번,미확인)/1(최소한번,중복가능)/2(정확히한번,4단계핸드셰이크)
- WebSocket = **단일 연결 위 양방향** 실시간 통신, 서버 푸시 가능 — SSE(서버→클라이언트 단방향)와 구분
- 실무 전형 패턴: 로봇↔서버는 MQTT, 서버↔대시보드는 WebSocket
