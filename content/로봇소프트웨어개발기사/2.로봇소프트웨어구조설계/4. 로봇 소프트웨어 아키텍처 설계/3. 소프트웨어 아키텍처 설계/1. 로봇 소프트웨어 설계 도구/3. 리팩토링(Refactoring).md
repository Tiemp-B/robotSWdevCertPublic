# Summary

**[[리팩토링(Refactoring)|리팩토링]]**은 소프트웨어의 **외부 동작(기능)은 그대로 유지**하면서 내부 코드 구조만 개선해 가독성·유지보수성을 높이는 활동이다.

# Notes

<aside>리팩토링의 목적</aside>

- **가독성 향상**: 이름이 불명확한 변수·함수 개선, 중복 코드 제거
- **유지보수성 향상**: 결합도를 낮추고 응집도를 높이는 구조로 재구성([[3. 모듈 결합도\|결합도]]·[[4. 모듈 응집도와 프로그램 구조\|응집도]] 개념 참고)
- **기술 부채 감소**: 시간이 지나며 쌓인 임시방편적 코드를 정리
- **버그 예방**: 복잡하게 얽힌 코드를 정리하면 잠재적 오류를 발견하기 쉬워짐

<aside>언제 리팩토링해야 하는가 — 코드 스멀(Code Smell)</aside>

리팩토링이 필요하다는 신호를 **[[코드 스멀과 Extract Method(Code Smell·Extract Method)|코드 스멀]]** 이라 한다. 버그는 아니지만 가독성·유지보수성을 떨어뜨리는 구조적 징후로, 하나의 메서드가 너무 많은 책임을 맡아 길어진 **긴 메서드(Long Method)** 가 대표적이다. 이를 해결하는 대표 기법이 **Extract Method** — 독립적인 역할을 하는 코드 덩어리를 찾아 이름을 붙여 별도 메서드로 분리하는 것이다. 각 메서드가 하나의 책임만 맡게 되는 방향은 결합도·응집도가 지향하는 바와도 통한다.

<aside>리팩토링과 테스트의 관계</aside>

리팩토링 전후로 소프트웨어의 동작이 실제로 바뀌지 않았음을 보장하려면, 리팩토링 전에 이미 검증된 테스트 케이스([[3. 시험 절차서와 테스트 케이스 작성|테스트 케이스]] 참고)가 갖춰져 있어야 하며, 리팩토링 직후 그 테스트를 다시 통과하는지 확인해야 한다.

<aside>예시 — 로봇 제어 코드의 리팩토링</aside>

**예시**: 여러 곳에 중복되어 있던 "장애물까지의 거리 계산" 로직을 하나의 공통 함수로 뽑아내고, 의미가 불분명하던 변수명(`d1`, `d2`)을 `frontDistance`, `sideDistance`처럼 명확하게 바꾸는 작업은 로봇의 동작(장애물 회피 결과)은 그대로 유지하면서 코드 구조만 개선하는 전형적인 리팩토링이다.

---

<aside>핵심 정리</aside>

- 리팩토링은 외부 동작을 바꾸지 않고 내부 구조만 개선하는 활동이며, 새 기능 추가와는 구분된다
- 코드 스멀(대표: 긴 메서드)은 리팩토링이 필요하다는 신호이며, Extract Method는 이를 해결하는 대표적인 기법이다
- 리팩토링 전후 동작이 동일함을 보장하려면 검증된 테스트 케이스가 뒷받침되어야 한다
