# Summary

통합 설계는 서브시스템 간 **인터페이스**를 명확히 정의하는 것에서 시작하며, 어떤 순서로 모듈을 결합할지에 대한 **통합 전략**(빅뱅 vs 점진적)을 함께 결정한다.

# Notes

<aside>인터페이스 설계</aside>

인터페이스 설계는 서브시스템 사이에 주고받는 데이터의 **형식·프로토콜·타이밍·오류 처리 방식**을 문서로 정의하는 작업이다. 이 정의가 명확하지 않으면 각 서브시스템을 개별적으로는 문제없이 개발했더라도, 통합 시점에 데이터 형식 불일치나 타이밍 오류가 드러난다.

- **데이터 형식**: 좌표계 단위(mm vs m), 데이터 구조(JSON, 바이너리 등)
- **프로토콜**: 어떤 통신 방식을 쓸지(1과목에서 다룬 발행-구독·요청-응답 등 [[3. 통신 모델(발행-구독·요청-응답·액션)|통신 패턴]] 참고)
- **타이밍**: 동기(synchronous) 호출인지 비동기(asynchronous) 호출인지, 최대 허용 지연시간
- **오류 처리**: 한쪽 모듈이 응답하지 않을 때 다른 쪽이 어떻게 대응할지

<aside>통합 전략 — 언제, 어떤 순서로 결합할 것인가</aside>

| 전략 | 방식 | 특징 |
|---|---|---|
| 빅뱅(Big-bang) | 모든 모듈을 한꺼번에 결합 | 통합 자체는 빠르지만, 오류 발생 시 원인 모듈을 찾기 어려움 |
| 점진적(하향식) | 상위 모듈부터 하위 모듈로 단계적으로 결합, 미구현 하위 모듈은 스텁으로 대체 | 상위 제어 로직을 일찍 검증 가능 |
| 점진적(상향식) | 하위 모듈부터 상위 모듈로 단계적으로 결합, 상위 모듈은 테스트 드라이버로 대체 | 하위 하드웨어 인터페이스를 일찍 검증 가능 |
| **샌드위치(혼합)** | 중간 계층을 기준으로 **위쪽은 하향식, 아래쪽은 상향식**을 동시에 진행 | 두 팀이 상위·하위 계층을 병렬로 개발·통합할 수 있어 인터페이스 결함을 상대적으로 일찍 발견 |

빅뱅·하향식·상향식 통합 기법 자체의 상세한 절차와 시험 방법은 [[4. 통합 시험 기법(빅뱅·하향식·상향식)|로봇 시스템 평가 절차]]에서 다루며, 여기서는 **통합 설계 단계에서 어떤 전략을 선택할지 결정**하는 관점에 집중한다. 샌드위치 통합은 이 세 방식 중 하향식·상향식을 동시에 적용하는 조합이다.

"로봇 시스템처럼 하드웨어와 소프트웨어가 얽힌 대규모 시스템은 항상 빅뱅 방식으로 통합하는 것이 가장 효율적이다"라는 서술은 오답이다 — 규모가 크고 결합도가 높은 시스템일수록 오류 위치 추적이 어려운 빅뱅 방식보다 **점진적 통합**이 일반적으로 더 적합하다.

<aside>예시 — 인터페이스 명세 문서화</aside>

**예시**: 센서 모듈 팀과 제어 모듈 팀이 각각 개발을 진행하기 전, "센서 모듈은 100ms 주기로 거리값(float, m 단위)을 JSON으로 발행하고, 제어 모듈은 이를 구독해 200ms 이상 값이 갱신되지 않으면 정지 명령을 내린다"는 인터페이스 규격을 문서로 합의해 두면, 두 팀이 독립적으로 개발하더라도 통합 시점의 충돌을 줄일 수 있다.

---

<aside>핵심 정리</aside>

- 인터페이스 설계는 서브시스템 간 데이터 형식·프로토콜·타이밍·오류 처리를 사전에 문서로 합의하는 작업이다
- 통합 전략은 빅뱅과 점진적(하향식·상향식) 방식으로 나뉘며, 대규모·고결합 시스템일수록 점진적 통합이 유리하다
- 샌드위치(혼합) 통합은 하향식·상향식을 동시에 적용해, 두 팀이 상위·하위 계층을 병렬로 통합할 수 있다
