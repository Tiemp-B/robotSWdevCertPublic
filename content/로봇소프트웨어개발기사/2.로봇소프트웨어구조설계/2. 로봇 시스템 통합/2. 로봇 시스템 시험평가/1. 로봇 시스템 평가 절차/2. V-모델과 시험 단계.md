# Summary

**[[V-모델(V-Model)|V-모델]]**은 소프트웨어 개발 단계(요구 사항 분석 → 설계 → 구현)와 그에 대응하는 시험 단계(단위 시험 → 통합 시험 → 시스템 시험 → 인수 시험)를 마주 보게 배치해, 개발의 역순으로 검증이 진행됨을 보여주는 모델이다.

# Notes

<aside>V-모델의 구조</aside>

| 개발 단계 | 대응하는 시험 단계 |
|---|---|
| 요구 사항 분석 | 인수 시험(Acceptance Test) |
| 시스템 설계 | 시스템 시험(System Test) |
| 아키텍처 설계 | 통합 시험(Integration Test) |
| 소프트웨어 모듈 설계 | 단위 시험(Unit Test) |
| 구현(코딩) | (좌우 접점 — 코딩 직후 단위 시험 시작) |

왼쪽 가지는 확인(Verification, "제품을 올바르게 만들었는가")을, 오른쪽 가지는 검증(Validation, "올바른 제품을 만들었는가")을 각각 나타낸다.

<aside>시험 단계별 특징</aside>

| 단계 | 검증 대상 | 검증 내용 |
|---|---|---|
| 단위 시험 | 개별 클래스·함수 | 알고리즘·로직·정확도·예외 처리 |
| 통합 시험 | 모듈 간 연동 | 매개변수 전달, 전역 데이터 손상, 동작 순서 오류 |
| 시스템 시험 | 배포 환경 전체 | 기능·비기능 시험, 인터럽트 처리, 자원 연결 문제 |
| 인수 시험 | 요구 사항 충족 여부 | 기능/성능/운용 요구 조건 만족 확인 |

<aside>정적 시험 vs 동적 시험</aside>

| 구분 | 방식 | 예 |
|---|---|---|
| 정적 시험 | 코드를 실행하지 않고 검토 | 코드리뷰, [[3. 정적 분석과 코딩 표준\|정적 분석 도구]] |
| 동적 시험 | 코드를 실제로 실행하며 검증 | 코드 실행률([[4. 동적 분석과 코드 커버리지\|코드 커버리지]])을 지표로 사용 |

<aside>블랙박스 시험 vs 화이트박스 시험</aside>

| 구분 | 관점 | 주 대상 단계 |
|---|---|---|
| 블랙박스 시험 | 내부 구조를 모르는 상태에서 입력·출력만으로 검증 | 시스템·인수 시험 |
| 화이트박스 시험 | 내부 로직·코드 경로를 알고 검증 | 단위·통합 시험 |

---

<aside>핵심 정리</aside>

- V-모델은 개발 단계와 시험 단계를 마주 배치한 모델로, 단위→통합→시스템→인수 시험 순으로 검증 범위가 넓어진다
- 정적 시험(코드 미실행)/동적 시험(코드 실행), 블랙박스(입출력 관점)/화이트박스(내부 로직 관점) 구분을 혼동하지 않아야 한다
