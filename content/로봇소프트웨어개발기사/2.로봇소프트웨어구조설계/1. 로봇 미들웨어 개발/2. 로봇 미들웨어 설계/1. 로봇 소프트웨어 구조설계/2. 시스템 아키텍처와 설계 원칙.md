# Summary

**[[시스템 아키텍처(System Architecture)|시스템 아키텍처]]**는 시스템의 구성과 동작 원리를 도식화한 것이다. 이를 설계할 때는 복잡한 문제를 한 번에 다루지 않고, **추상화**로 큰 그림을 먼저 잡은 뒤 **단계적 정제**로 점차 구체화하며, **정보 은닉**으로 각 부분이 서로에게 미치는 영향을 최소화한다.

# Notes

<aside>시스템 아키텍처란</aside>

시스템의 구성 요소, 요소 간의 관계, 시스템과 외부 환경의 관계를 도식화해 표현한 것이다. 시스템이 어떻게 작동하는지 — 구동 목적을 위해 각 요소가 무엇이며 어떻게 정보를 교환하는지 — 를 기술한다.

<aside>추상화(Abstraction)</aside>

세부 사항을 먼저 설계하기보다, **전체적이고 포괄적인 개념을 먼저 설계한 뒤 점진적으로 세분화**하는 방법이다. 설계가 상세해질수록 추상화 수준은 낮아지고, 원시 코드가 만들어질 때 추상화는 최하위 수준이 된다.

| 추상화 종류 | 내용 |
|---|---|
| 기능의 추상화 | 입력을 출력으로 변환하는 과정을 추상화 |
| 제어의 추상화 | 제어 절차를 정의하지 않고 원하는 효과만 정함 |
| 자료의 추상화 | 자료와 그 자료에 적용될 기능을 함께 정의해 자료 개체를 구성 |

<aside>단계적 정제(Stepwise Refinement)</aside>

니클라우스 비르트가 제안한 **하향식(top-down)** 설계 전략이다. 상위의 중요 개념에서 하위의 세부 개념으로 점차 구체화하는 분할 기법으로, 소프트웨어 기능에서 시작해 점차 구체화하고, 상세한 알고리즘·자료구조 같은 세부 사항은 가능한 한 뒤로 미룬다.

<aside>정보 은닉(Information Hiding)</aside>

필요하지 않은 정보는 외부에서 접근할 수 없도록 제외해, 하위 구조·모듈의 구체적인 구현 내용과 내부 정보를 다른 모듈의 접근으로부터 통제하는 것이다. 정의된 인터페이스(메시지)를 통해서만 접근·전달이 이뤄지도록 해, 한 모듈의 설계 변경이 다른 모듈에 미치는 영향을 최소화한다. 숨겨야 할 기본 정보로는 상세한 데이터 구조, 하드웨어 디바이스 제어 부분, 특정 운영체제·DBMS에 의존하는 부분, IP 주소 같은 물리적 코드 등이 있다.

<aside>모듈화(Modularity)</aside>

소프트웨어를 각 기능별로 분할하는 것이다. 모듈화하면 소프트웨어의 복잡도가 감소하고, 변경·구현이 쉬워지며 확장성·경제성이 향상된다. 모듈 간의 의존 정도(결합도)와 모듈 내부의 응집 정도(응집도)는 [[3. 모듈 결합도|다음 페이지]]에서 다룬다.

<aside>예시 — 긴급 정지 기능의 단계적 정제</aside>

**예시**: 로봇의 "긴급 정지 및 해지" 기능을 설계할 때, 먼저 "긴급 정지"와 "해지"라는 큰 개념만 잡고(추상화), 이후 "패널/조작반 구분 → 서보 온 레디 버튼 또는 데드맨 스위치 확인"처럼 점차 세부 절차로 구체화(단계적 정제)하며, 각 버튼·스위치의 내부 신호 처리는 해당 모듈 안에 감춰(정보 은닉) 다른 모듈이 몰라도 되게 설계한다.

---

<aside>핵심 정리</aside>

- 시스템 아키텍처는 시스템의 구성·동작 원리를 도식화한 것이다
- 추상화(기능/제어/자료)로 큰 그림을 먼저 잡고, 단계적 정제(하향식)로 점차 구체화하며, 정보 은닉으로 모듈 간 영향을 최소화하는 것이 설계의 기본 원칙이다
- 정보 은닉의 목적은 정보 교환을 늘리는 것이 아니라 불필요한 노출을 막는 것이다
