# Summary

[[3. UML과 행위적 다이어그램|행위적 다이어그램]]이 객체의 동작·상태 변화를 표현한다면, **구조적 다이어그램**은 처리 과정의 흐름과 시스템을 이루는 구성 요소 자체를 표현한다. NCS 학습모듈에서는 activity·class·component·deployment 다이어그램을 이 범주로 분류한다.

# Notes

<aside>activity diagram</aside>

오퍼레이션이나 처리 과정이 수행되는 동안 일어나는 일들을 간단하게 표현한다. **처리 단계·결정 위치(분기)·병행 처리**를 표현할 수 있어, 업무 과정이나 로봇의 동작 절차를 나타내는 데 널리 쓰인다. 시작점·종료점, 마름모(결정 분기), 굵은 선(동시 실행 분기)으로 구성된다.

<aside>class diagram</aside>

**클래스(class)**를 표현하는 양식으로, 클래스 이름·속성(attribute)·오퍼레이션(행위)을 포함한다. 클래스 간의 관계(연관, 상속 등)를 표현하는 데 사용된다.

class diagram과 짝을 이루는 것이 **오브젝트(object) 다이어그램**이다. class diagram이 클래스라는 "추상적인 설계도"를 표현한다면, object diagram은 그 클래스의 실제 **인스턴스(객체)** 를 특정 시점의 속성 값과 함께 나타낸 "런타임 스냅샷"이다 — 설계도(class)와, 그 설계도로 만들어진 실제 사물의 한 순간(object)의 관계로 이해할 수 있다.

<aside>component diagram</aside>

소프트웨어 **컴포넌트의 구성과 연결 상태**를 나타낸다. 컴포넌트는 시스템을 이루는 물리적 요소(데이터 파일, 실행 파일, 도큐먼트 등)로, "클래스를 소프트웨어로 구현한 것"으로 간단히 정의할 수 있다.

<aside>deployment diagram</aside>

시스템의 **소프트웨어와 하드웨어 컴포넌트 간의 물리적 관계**를 표현한다. 어떤 소프트웨어가 어떤 물리적 장치에 배치(deploy)되는지를 보여준다.

<aside>로봇 미들웨어 아키텍처 설계에 적합한 다이어그램 선택</aside>

로봇의 특정 기능(예: 긴급 정지·해지 기능)에 대한 미들웨어 아키텍처를 설계할 때는, 그 기능의 성격에 맞는 다이어그램을 선택해야 한다.

| 상황 | 적합한 다이어그램 |
|---|---|
| 순차적인 절차·처리 단계 표현 | sequence diagram, **activity diagram** |
| 그룹·구성 요소 관계 표현 | class diagram, component diagram |
| 물리적 배치 관계(복잡) | deployment diagram |

<aside>예시 — 로봇 긴급 정지 기능의 activity diagram</aside>

**예시**: "로봇 운전 → 긴급 정지 버튼 누름 → 로봇 정지 → [패널 버튼 해지되었나?]/[조작반 버튼 해지되었나?] 분기 → 서보 온 레디 버튼 또는 데드맨 스위치 확인 → 로봇 동작 재개"처럼, 로봇의 긴급 정지·해지 절차를 분기와 함께 activity diagram으로 표현하면 전체 흐름을 한눈에 파악할 수 있다.

---

<aside>핵심 정리</aside>

- activity(처리 흐름·분기·병행), class(속성+오퍼레이션), component(컴포넌트 구성), deployment(SW-HW 물리적 배치)가 구조적 다이어그램이다
- object diagram은 class diagram(추상적 설계도)의 실제 인스턴스를 특정 시점의 값과 함께 보여주는 런타임 스냅샷이다
- 처리 과정의 순서·분기를 표현하는 데는 activity diagram이 적합하며, 이를 use case diagram과 혼동하면 안 된다
