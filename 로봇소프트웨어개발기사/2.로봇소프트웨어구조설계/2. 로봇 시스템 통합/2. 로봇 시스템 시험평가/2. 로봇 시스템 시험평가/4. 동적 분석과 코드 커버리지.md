# Summary

**동적 분석**은 프로그램을 실제로 실행하며 검증하는 방법으로, **[[코드 커버리지(Code Coverage)|코드 커버리지]]** (코드 실행률)를 주요 지표로 삼는다. 커버리지에는 문장·분기·MC/DC 등 여러 수준이 있으며, 수준이 높을수록 더 많은 테스트 케이스가 필요하다.

# Notes

<aside>코드 커버리지의 종류</aside>

| 커버리지 | 판단 기준 | 특징 |
|---|---|---|
| 문장 커버리지(statement) | 각 코드 문장이 한 번이라도 실행되었는가 | 작성이 가장 쉽지만 보장성이 가장 낮음(조건문의 True/False를 모두 확인하지 못함) |
| 분기 커버리지(branch) | 조건문의 True/False 결과가 각각 한 번씩 나왔는가 | 문장 커버리지보다 엄격하지만, 조건문 내부 개별 조건까지는 분리해 확인하지 않음 |
| 변형다중조건 커버리지(MC/DC) | 조건문 내 각 개별 조건이 독립적으로 결과에 영향을 미치는 경우까지 확인 | 세 가지 중 가장 엄격 |

"문장 커버리지 100%를 달성했다면 프로그램에 논리적 결함이 없다고 볼 수 있다"라는 서술은 오답이다 — 문장 커버리지는 코드가 **한 번이라도 실행되었는지만** 확인할 뿐, 조건문의 각 분기 결과나 개별 조건의 조합까지 검증하지는 못하므로 결함이 없다는 근거가 될 수 없다.

<aside>분기 커버리지 100%를 위한 테스트 케이스 설계</aside>

조건이 `if(a==1 && b==1)`처럼 여러 조건이 결합된 경우, 분기 커버리지 100%를 만족시키려면 전체 결과가 True인 경우 1개, False인 경우 1개, 총 2개의 테스트 케이스만 있으면 된다(개별 조건 a, b의 모든 조합을 다 시험할 필요는 없다 — 그것은 MC/DC의 몫이다).

<aside>정적 분석과 동적 분석의 상호 보완</aside>

정적 분석([[3. 정적 분석과 코딩 표준|앞 페이지]])은 실행 전에 코드 구조상의 결함을 찾고, 동적 분석은 실제 실행 결과가 요구 사항과 일치하는지 확인한다는 점에서 서로 보완적이다. 정적 분석에서 오류가 없다고 나왔더라도 동적 분석(실제 실행)에서 요구 사항과 다른 결과가 나올 수 있으므로, 두 분석을 모두 수행해야 신뢰성을 확보할 수 있다.

<aside>예시 — 분기 커버리지 테스트 케이스 산출</aside>

**예시**: 로봇의 X축 위치에 따라 초록/노란/빨강 LED를 표시하는 로직처럼 여러 개의 `if-else` 분기가 연쇄된 코드에서, 분기 커버리지 100%를 달성하려면 흐름도상 각 조건 분기의 True/False 경로를 모두 지나는 최소 개수의 입력값 조합(예: 두 개의 조건문이면 2개)을 테스트 케이스로 설계한다.

---

<aside>핵심 정리</aside>

- 코드 커버리지는 문장 < 분기 < MC/DC 순으로 엄격해지며, 문장 커버리지 100%가 결함 없음을 보장하지는 않는다
- 정적 분석과 동적 분석은 서로 보완적이며, 둘 다 수행해야 신뢰성을 충분히 확보할 수 있다
