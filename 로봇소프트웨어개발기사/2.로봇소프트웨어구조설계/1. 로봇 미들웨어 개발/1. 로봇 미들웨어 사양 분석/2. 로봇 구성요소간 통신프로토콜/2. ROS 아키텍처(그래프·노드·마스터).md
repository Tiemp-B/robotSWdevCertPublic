# Summary

ROS는 **그래프 기반 아키텍처**를 채택한다. 하나의 로봇 시스템은 연산을 수행하는 여러 **노드(Node)**로 구성되며, 노드들은 **마스터(Master)**의 중개로 서로를 찾아 [[3. 통신 모델(발행-구독·요청-응답·액션)|Topic·Service]]를 통해 통신한다.

# Notes

<aside>노드(Node)</aside>

ROS에서 **노드**는 연산을 수행하는 하나의 프로세스다. 하나의 로봇 시스템은 일반적으로 많은 수의 노드로 구성되며(예: 카메라 노드, 모터 제어 노드, 경로 계획 노드), 각 노드는 독립된 프로세스로 실행된다.

<aside>마스터(Master)</aside>

**마스터**는 노드들이 서로를 찾을 수 있도록 중개하는 역할을 한다. 노드가 시작되면 마스터에 자신의 정보(어떤 토픽을 발행/구독하는지 등)를 등록하고, 마스터는 이 정보를 바탕으로 서로 통신해야 할 노드들끼리 **접속 정보**를 교환하도록 안내한다.

- 마스터가 중개하는 것은 **접속 정보 교환**까지이며, 일단 연결이 성립되면 노드 간의 실제 메시지 통신(토픽 데이터 전달)은 마스터를 거치지 않고 노드끼리 직접 이뤄진다. "모든 메시지는 항상 마스터를 거쳐 중계된다"는 서술은 이 구조를 오해한 오답이다.

<aside>패키지(Package)</aside>

ROS는 노드의 실행 파일, 설정 파일, 라이브러리 등을 **패키지**라는 단위로 묶어 배포한다. 로봇 소프트웨어 모듈을 구성하는 기본 배포 단위가 패키지다.

<aside>ROS 통신 기능의 하드 코딩 문제</aside>

ROS는 각 노드를 위한 명시적인 컴포넌트 모델을 갖고 있지 않고, 토픽·서비스 호출을 통해 프로세스 간 통신(IPC)을 제공하는 형태다. 이 때문에 노드들이 서로 어떻게 연결되는지가 각 노드 프로그램 코드에 직접 작성(하드 코딩)되어 있어, **시스템 설계 시점에 전체 구성을 한눈에 파악하기 어렵고**, 실제 실행해 봐야 연결 관계를 확인할 수 있다는 한계가 있다.

<aside>예시 — ROS 노드 구성</aside>

**예시**: 이동로봇 시스템은 카메라 노드(이미지를 Topic으로 발행), 장애물 인식 노드(카메라 Topic을 구독해 처리 결과를 다시 발행), 경로 계획 노드(위치 정보를 요청-응답 방식으로 조회)처럼 여러 노드로 나뉘어 동작하며, 각 노드는 마스터에 등록된 정보를 바탕으로 서로 필요한 상대를 찾아 직접 통신한다.

---

<aside>핵심 정리</aside>

- ROS는 그래프 기반 아키텍처로, 노드(연산을 수행하는 프로세스)들의 연결로 구성된다
- 마스터는 노드 간 접속 정보 교환을 중개할 뿐이며, 실제 메시지 통신은 노드끼리 직접 이뤄진다
- 패키지는 노드 실행 파일·설정·라이브러리를 묶은 배포 단위다
- 노드 간 연결 관계가 코드에 하드 코딩되어 있어, 설계 시점에 전체 구성을 파악하기 어렵다는 한계가 있다
