# Summary

**캡슐화(Encapsulation)**는 객체의 내부 상태를 외부로부터 숨기는 원칙이며, **[[SOLID 원칙(SOLID Principles)|SOLID]]**는 이를 포함해 변경에 강한 객체지향 설계를 위한 5가지 원칙의 모음이다.

# Notes

<aside>캡슐화(Encapsulation)의 목적</aside>

캡슐화는 객체의 데이터(속성)와 그 데이터를 다루는 메서드를 하나로 묶고, **외부에서는 정해진 인터페이스(메서드)를 통해서만 데이터에 접근**하도록 제한하는 원칙이다.

- 내부 구현이 바뀌어도 외부 인터페이스만 유지되면 다른 코드에 영향을 주지 않음
- 데이터가 잘못된 값으로 직접 변경되는 것을 방지(유효성 검사를 메서드 안에서 강제)

"캡슐화의 목적은 객체의 모든 속성과 메서드를 외부에서 자유롭게 직접 접근·수정할 수 있게 하는 것이다"라는 서술은 오답이다 — 캡슐화의 핵심은 오히려 내부 데이터에 대한 **직접 접근을 제한**하고, 정해진 인터페이스를 통해서만 접근하도록 하는 것이다.

<aside>SOLID 원칙</aside>

| 원칙 | 이름 | 핵심 |
|---|---|---|
| S | 단일 책임 원칙(SRP) | 클래스는 하나의 책임만 가져야 함 |
| O | 개방-폐쇄 원칙(OCP) | 확장에는 열려 있고, 수정에는 닫혀 있어야 함 |
| L | **리스코프 치환 원칙(LSP)** | **상위 클래스와 하위 클래스는 서로 교체 가능해야 함** |
| I | 인터페이스 분리 원칙(ISP) | 클라이언트가 사용하지 않는 인터페이스에 의존하지 않아야 함 |
| D | 의존관계 역전 원칙(DIP) | 구체적 구현이 아닌 추상화에 의존해야 함 |

"SOLID 원칙 중 상위 클래스와 하위 클래스 사이의 상호 교체 가능성을 의미하는 원칙은 개방-폐쇄 원칙(OCP)이다"라는 서술은 오답이다 — 상위·하위 클래스의 상호 교체 가능성은 **리스코프 치환 원칙(LSP)**이며, 개방-폐쇄 원칙은 기존 코드 수정 없이 기능을 확장할 수 있어야 한다는 원칙이다.

<aside>예시 — 로봇 센서 클래스에 SOLID 적용</aside>

**예시**: `Sensor` 상위 클래스를 상속받은 `UltrasonicSensor`, `LidarSensor` 하위 클래스가 `Sensor` 타입을 요구하는 모든 코드에서 문제없이 대체되어 동작한다면 리스코프 치환 원칙을 만족하는 것이며, 새로운 센서 타입(`CameraSensor`)을 추가할 때 기존 `Sensor` 관련 코드를 수정하지 않고 새 클래스만 추가해 확장할 수 있다면 개방-폐쇄 원칙을 만족하는 것이다.

---

<aside>핵심 정리</aside>

- 캡슐화는 내부 데이터에 대한 직접 접근을 제한하고 정해진 인터페이스로만 접근하게 하는 것이다
- SOLID의 L(리스코프 치환 원칙)은 상위·하위 클래스의 교체 가능성을 의미하며, O(개방-폐쇄 원칙)와 자주 혼동된다
