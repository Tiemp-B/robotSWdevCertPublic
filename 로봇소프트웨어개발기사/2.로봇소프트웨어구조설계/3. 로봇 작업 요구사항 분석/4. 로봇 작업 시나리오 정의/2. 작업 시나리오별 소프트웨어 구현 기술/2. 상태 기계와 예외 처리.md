# Summary

**상태 기계(State Machine)**로 시나리오를 구현하면 로직이 상태별로 명확히 분리되어 유지보수가 쉬워지며, 로봇 소프트웨어는 예측 불가능한 상황이 많으므로 시나리오 설계 단계에서부터 **예외 처리**를 빠짐없이 정의해야 한다.

# Notes

<aside>상태 기계(State Machine)의 장점</aside>

상태 기계는 시스템의 동작을 유한한 개수의 상태와, 상태 간 전이(사건에 의해 발생)로 표현하는 구현 방식이다([[3. UML과 행위적 다이어그램|statechart diagram]]으로 설계한 것을 코드로 옮긴 형태).

- **로직의 명확한 분리**: "지금 어떤 상태인가"에 따라 처리할 코드가 명확히 구분되어 조건문이 뒤섞이는 것을 방지
- **예측 가능한 전이**: 허용되지 않은 상태 전이를 원천적으로 차단할 수 있어 오동작 방지
- **유지보수 용이성**: 새로운 상태나 전이를 추가할 때 기존 로직을 크게 건드리지 않아도 됨
- **테스트 용이성**: 상태별로 독립적인 테스트 케이스 작성이 쉬움

"상태 기계의 장점은 모든 예외 상황을 자동으로 처리해 별도의 예외 처리 코드가 필요 없다는 것이다"라는 서술은 오답이다 — 상태 기계는 로직을 명확히 구조화할 뿐, 예외 상황에 대한 처리는 **개발자가 별도로 정의**해야 한다.

<aside>예외 처리(Exception Handling)가 필요한 상황</aside>

로봇은 정해진 시나리오대로만 동작하지 않는 경우가 많으므로, 다음과 같은 상황에는 예외 처리가 반드시 필요하다.

- 센서 값이 비정상적이거나 통신이 끊긴 경우
- 예상 범위를 벗어난 입력(장애물이 갑자기 나타남 등)
- 액추에이터가 명령을 수행하지 못하는 경우(과부하, 고장 등)
- 사용자가 시나리오 도중 긴급 정지를 요청하는 경우

반대로 "모든 로봇 작업 시나리오는 예외 처리 없이도 안전하게 동작할 수 있다"라는 서술은 오답이다 — 통신이 두절되거나 장애물이 예기치 않게 나타나는 등 예외적 상황을 사전에 배제할 수 없는 이상, 예외 처리는 시나리오 설계에서 빠질 수 없는 요소다. 특히 [[2. 로봇 동작 환경의 분류|동적 환경]]처럼 변화가 예상되는 상황일수록 예외 처리의 필요성이 커진다.

<aside>예시 — 상태 기계로 구현한 배송 로봇 시나리오</aside>

**예시**: 배송 로봇을 "대기 → 이동 중 → 배송 완료" 상태 기계로 구현하면, "이동 중" 상태에서 장애물을 만나 통신이 끊기는 예외가 발생했을 때 "이동 중" 상태에서만 유효한 예외 처리 로직(안전 정지 후 재연결 대기)을 명확히 분리해 작성할 수 있다.

<aside>핵심 정리</aside>

- 상태 기계는 로직을 상태별로 명확히 분리해 유지보수·테스트를 쉽게 하지만, 예외 처리는 개발자가 별도로 정의해야 한다
- 예외 처리는 센서 이상, 통신 두절, 예상 밖 입력, 액추에이터 고장 등에 필요하며 동적 환경일수록 중요성이 커진다
