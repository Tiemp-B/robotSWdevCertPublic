# Summary

**[[세션(Session)|세션]]**은 [[1. 서버 프로그램 개요|상태유지(Stateful) 서버]]가 클라이언트별 상태를 유지하는 대표적 방법으로, **클라이언트 측에는 데이터를 저장하지 않고 서버 측에서 발급한 세션 ID만 클라이언트에 전달**하는 방식이다. 실제 상태 데이터는 서버(또는 서버가 공유하는 저장소)에 남고, 클라이언트는 그 데이터를 가리키는 식별자만 들고 다닌다.

# Notes

<aside>세션의 동작 흐름</aside>

1. 클라이언트가 로그인 요청
2. 서버가 인증 성공 시 세션을 생성하고 세션 저장소에 상태를 저장
3. 서버가 클라이언트에 세션 ID를 발급(보통 쿠키에 담아 전달)
4. 클라이언트는 이후 요청마다 세션 ID를 함께 전송
5. 서버는 세션 ID로 저장소를 조회해 해당 클라이언트의 상태를 파악

"클라이언트 측에 데이터를 저장하지 않고 서버 측에서 세션 ID만을 발급하여 관리"한다는 서술이 바로 이 방식의 정의다.

<aside>쿠키와의 차이</aside>

| 항목 | 쿠키(Cookie) | 세션(Session) |
|---|---|---|
| 데이터 저장 위치 | 클라이언트(브라우저) | 서버(또는 공유 저장소) |
| 클라이언트가 보관하는 것 | 데이터 자체 | 세션 ID(식별자)뿐 |

쿠키 자체의 세부 특성(만료, 도메인 제한 등)은 [[1. 클라이언트 프로그램 개요]] 세세항목에서 다루며, 여기서는 "상태를 어디에 저장하는가"라는 구조적 차이에 집중한다.

<aside>세션 저장 방식</aside>

| 저장 위치 | 특징 |
|---|---|
| 서버 메모리 | 빠르지만 서버 재시작 시 소실, 그 서버에서만 유효 |
| 데이터베이스 | 영속적이지만 조회 지연 발생 |
| 분산 캐시(Redis 등) | 여러 서버가 세션 저장소를 공유 가능 — [[5. 로드밸런싱과 확장성]]과 직결 |

<aside>JWT 기반 무상태 인증과의 비교</aside>

| 항목 | 세션 방식 | [[JWT(JSON Web Token)\|JWT]] 방식 |
|---|---|---|
| 상태 저장 위치 | 서버(세션 저장소) | 클라이언트(토큰 자체에 정보 포함) |
| 서버 확장성 | 여러 서버 간 세션 공유 필요 | 서버가 상태를 안 가지므로 수평 확장에 유리 |
| 즉시 무효화 | 서버에서 세션 삭제로 즉시 가능 | 토큰 자체 무효화가 어려움(만료 시간에 의존, 즉시 차단하려면 별도 블랙리스트가 필요해 결국 다시 상태를 갖게 됨) |

<aside>세션과 로드밸런싱의 상호작용</aside>

서버가 여러 대로 늘어나면(로드밸런싱), 세션을 한 서버의 메모리에만 저장할 경우 **다른 서버가 같은 클라이언트의 요청을 받으면 세션을 찾지 못하는 문제**가 생긴다. 이는 [[5. 로드밸런싱과 확장성]]에서 다룰 **스티키 세션(Sticky Session)**이나 세션 저장소 공유(분산 캐시)로 해결한다.

<aside>예시 — 로봇 원격제어 대시보드 로그인</aside>

**예시**: 운영자가 관제 대시보드에 로그인하면 서버가 세션을 생성하고 세션 ID를 쿠키로 내려준다. 이후 운영자가 특정 로봇에 정지 명령을 보낼 때마다, 서버는 요청에 담긴 세션 ID로 해당 운영자의 로그인 상태와 권한을 확인한 뒤 명령을 처리한다.

---

<aside>핵심 정리</aside>

- 세션은 **서버 측에 상태를 저장하고 클라이언트에는 세션 ID만 발급** — 데이터 자체를 저장하는 쿠키와 대비
- 저장 위치는 메모리/DB/분산 캐시 중 선택, 서버가 여러 대일 때는 분산 캐시 공유가 필요
- JWT는 서버가 상태를 저장하지 않는 대안 — 확장성은 유리하나 즉시 무효화가 어려움
- 세션과 로드밸런싱은 "여러 서버 간 상태를 어떻게 공유할 것인가"로 직결
