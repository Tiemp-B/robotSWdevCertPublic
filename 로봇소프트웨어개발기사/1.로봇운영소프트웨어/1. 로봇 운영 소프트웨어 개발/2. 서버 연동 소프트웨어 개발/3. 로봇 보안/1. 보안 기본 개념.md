# Summary

보안의 기본 목표는 **[[CIA 트라이어드(CIA Triad)|CIA 트라이어드]]**(기밀성·무결성·가용성, NIST/ISO 27001 공통 기준)로 요약되며, 이 중 **인가된 사용자만 정보에 접근하도록 하는 것이 기밀성(Confidentiality)**이다. 기밀성을 지키려면 먼저 "누구인지 확인하는" **[[인증(Authentication)|인증]]**과 "그 사용자가 무엇을 할 수 있는지 결정하는" **[[인가(Authorization)|인가]]**를 구분해야 하며, 이 인증을 실제로 구현하는 대표적 방식이 세션 기반 인증과 JWT 기반 인증이다.

# Notes

<aside>CIA 트라이어드</aside>

| 요소 | 의미 |
|---|---|
| 기밀성(Confidentiality) | 인가된 사용자만 정보에 접근할 수 있도록 보장 |
| 무결성(Integrity) | 정보가 무단으로 변조되지 않았음을 보장 |
| 가용성(Availability) | 필요할 때 정보·서비스에 정상적으로 접근할 수 있도록 유지 |

"인가된 사용자만이 정보에 접근할 수 있도록 하는 보안 요소"는 이 중 **기밀성(Confidentiality)**에 해당한다.

<aside>인증(Authentication)과 인가(Authorization)</aside>

| 항목 | 인증 | 인가 |
|---|---|---|
| 질문 | "당신은 누구인가?" | "이 사용자는 무엇을 할 수 있는가?" |
| 예시 | 아이디/비밀번호 로그인, 생체 인증 | 관리자만 로봇 설정 변경 가능, 일반 운영자는 조회만 가능 |
| 순서 | 먼저 신원을 확인 | 확인된 신원을 바탕으로 권한 부여 |

"인증과 인가는 같은 개념이다"는 옳지 않다 — 인증은 신원 확인, 인가는 그 신원에 대한 권한 부여로 뚜렷이 구분된다.

<aside>인증 구현 방식 ① 세션 기반</aside>

[[3. 세션과 상태 관리]]에서 다룬 대로, 로그인 성공 시 서버가 세션을 생성하고 세션 ID를 클라이언트에 발급하는 방식이다. 세션 ID가 탈취되면 곧 계정 탈취로 이어지므로(**세션 하이재킹**), HTTPS로 통신을 암호화하고 [[5. 쿠키(Cookie) 기반 세션 관리|쿠키의 HttpOnly/Secure 속성]]을 반드시 적용해야 한다.

<aside>인증 구현 방식 ② JWT 기반</aside>

JWT는 서버가 상태를 저장하지 않는 대신, 토큰 자체에 **서명(Signature)**을 포함한다. 서버는 비밀키(또는 공개키)로 토큰의 서명을 검증해, 발급 이후 내용이 변조되면 서명 검증이 실패하도록 만든다. 다만 토큰이 탈취되면 만료 시점 전까지 무효화하기 어렵다는 한계는 여전히 남는다.

<aside>세션 vs JWT — 보안 관점 비교</aside>

| 항목 | 세션 | JWT |
|---|---|---|
| 즉시 무효화 | 서버에서 세션 삭제로 즉시 가능 | 어려움(만료 시간에 의존) |
| 검증 방식 | 매 요청마다 세션 저장소 조회 | 서명 검증만으로 자체 확인 가능 |
| 공격 대상 | 세션 저장소 자체가 표적이 될 수 있음 | 탈취된 토큰이 만료 전까지 악용될 수 있음 |

<aside>예시 — 로봇 관제 시스템의 인증/인가 흐름</aside>

**예시**: 운영자가 아이디/비밀번호로 로그인하면(인증), 시스템은 그 운영자의 역할(관리자 vs 일반 운영자)에 따라 특정 로봇에 대한 정지/설정변경 권한을 다르게 부여한다(인가). 이 인증 상태는 세션 또는 JWT 중 한 방식으로 이후 요청마다 유지된다.

<aside>핵심 정리</aside>

- CIA 트라이어드는 기밀성·무결성·가용성이며, "인가된 사용자만 접근 가능하게 하는 것"은 **기밀성**
- 인증은 "누구인가"를 확인하고, 인가는 "무엇을 할 수 있는가"를 결정하며, 인증이 먼저 이뤄짐
- 세션 인증은 즉시 무효화가 쉽지만 세션 저장소가 표적이 될 수 있고, JWT는 자체 검증이 가능하지만 탈취 시 즉시 무효화가 어려움
